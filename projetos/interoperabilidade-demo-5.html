Creating a Foreign Catalog Connection to AWS Glue Catalog

Data Interoperability with Unity Catalog · Demo 5

Em desenvolvimento

Esta demo, de cerca de 7 minutos e meio, federa o AWS Glue Catalog no Unity Catalog. O padrão é o mesmo da demo anterior (connection + foreign catalog), mas o Glue é um catálogo de metadados, e não um banco. Por isso há uma camada a mais: credenciais separadas para os metadados do Glue e para os dados no S3.

Estas anotações partem de um resumo da demo, não da transcrição. Segundo o resumo, a única legenda do vídeo está em chinês simplificado, e o resumo foi feito a partir dela. O resumo não traz o texto das políticas nem dos comandos, e por isso não escrevi código aqui.

Pré-requisitos

  • Metastore admin, para criar as credenciais, a external location, a connection e o foreign catalog.
  • IAM admin na conta AWS, para criar as roles e as trust policies.
  • Um Glue catalog existente, com tabelas e dados no S3.

O exemplo é o dataset de voos (flights), de um banco Glue: um conjunto de arquivos CSV no S3.

A visão geral dos passos

A role de acesso ao Glue (service credential)

A primeira IAM role é a Databricks Glue access role.

  • A trust policy permite que ela seja assumida pela role principal do Unity Catalog e por ela mesma (self-assuming). O external ID e a condição começam como um placeholder (0000), e são substituídos depois pelo valor real emitido pelo Unity Catalog.
  • A permissions policy é de menor privilégio: só leitura do Glue (GetDatabase, GetTable e GetPartitions), sem escrita nem outros serviços.

Registra-se a role no Unity Catalog como uma credencial, pela CLI (o nome, purpose = service e o ARN). A resposta traz um external ID, que se copia para a trust policy da role. Isso completa o handshake: só o Unity Catalog, com aquele external ID, pode assumi-la.

A role de acesso ao storage e a external location

A primeira role só acessa os metadados, então cria-se uma segunda, a DatabricksGlueStorageAccessRole, limitada ao bucket S3, com permissão de somente leitura (sem put nem delete). Como o foreign catalog é só leitura, a escrita só ampliaria a superfície de ataque.

  1. Registra-se a role no Unity Catalog com purpose = storage (a mesma ideia da CLI anterior).
  2. Pega-se o novo external ID e atualiza-se a trust policy.
  3. Cria-se uma external location, que mapeia um nome lógico do Unity Catalog a um caminho S3 físico, pareada com a storage credential. O foreign catalog a referenciará nos authorized paths.

Detalhe do skip validation: usa-se a flag skip validation, porque a role é somente leitura e a validação padrão do Unity Catalog faz um teste de escrever e apagar, que falharia. É seguro pular, porque a leitura já foi verificada na IAM role.

Connection e foreign catalog

Com a AWS pronta, a connection do tipo Glue recebe o aws_account_id, a região (o escopo é regional) e a service credential. Valida-se com o DESCRIBE CONNECTION.

Em seguida, o foreign catalog usa a connection e os authorized paths, que batem com a localização S3 das tabelas do Glue e com a storage credential. O DESCRIBE CATALOG confirma o tipo foreign.

Consulta e caminho de migração

A consulta ao dataset de flight status precisa de crases (backticks), porque o banco e a tabela têm hífens. Os foreign catalogs são somente leitura por design.

O caminho natural para trazê-los à governança plena do Unity Catalog é foreign → external → managed:

EstágioQuem é dono
ForeignO Unity Catalog só lê o Glue
ExternalO Unity Catalog é dono dos metadados, e os dados ficam no S3 do Glue
ManagedO Unity Catalog é dono dos metadados e dos dados

Usam-se o SET EXTERNAL e o SET MANAGED para promover as tabelas sem reescrever os dados, quando possível.

Resumo

  • Duas IAM roles de menor privilégio, separando os metadados e os dados.
  • Duas credenciais no Unity Catalog (service e storage).
  • Uma external location para o caminho S3.
  • Uma connection e um foreign catalog, com authorized paths.

Assim as tabelas do Glue ficam consultáveis a partir do Unity Catalog sem mover dados, com a trilha foreign, external e managed para a migração.

Ligação com as outras páginas: as credenciais e a external location são os conceitos de fontes baseadas em arquivos da lição Centralized Governance and Visibility, e a diferença entre tabela gerenciada e externa está na lição Unity Catalog Fundamentals. Na Demo 4, o padrão connection + foreign catalog é o mesmo. As ligações são minhas.

O que guardar: para federar o Glue, separe o acesso aos metadados (uma credencial service) do acesso aos dados (uma credencial storage e uma external location), com roles IAM de menor privilégio e o handshake do external ID. Depois, crie a connection do tipo Glue e o foreign catalog com authorized paths. Foreign catalogs são só leitura, e a trilha de migração é foreign, external e managed.
