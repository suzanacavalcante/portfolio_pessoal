Os três tipos de dataset

ST

Streaming tables

Suportam processamento streaming e incremental, processando apenas os dados novos.

MV

Materialized views

Processam os registros necessários para dar resultados corretos sobre o estado atual dos dados. Servem para transformações, agregações, pré-cálculo de consultas lentas e cálculos frequentes.

View

Views

Uma tabela virtual sem dados físicos, baseada na consulta do pipeline. Há dois tipos: Temporary View e View.

Streaming table

Processa só os dados novos, conforme chegam, em vez de reprocessar tudo a cada execução. O ganho é eficiência e menor custo. Os pontos principais:

  1. Processamento incremental, em batch ou em streaming, com processamento exactly-once de arquivos.
  2. Atualizações eficientes: a cada refresh, os dados novos da origem são anexados (append).
  3. O comando SQL é o CREATE OR REFRESH STREAMING TABLE.
  4. A leitura é FROM STREAM read_files(), que habilita a leitura incremental com checkpoint.
  5. A integração é com o Auto Loader, que rastreia os arquivos novos de forma confiável.
  6. Sem leituras duplicadas: cada arquivo é lido uma única vez.

Bronze: orders_bronze

Os passos são o CREATE OR REFRESH STREAMING TABLE, a cláusula SELECT e a fonte streaming (o FROM). A consulta usa o catálogo padrão.

CREATE OR REFRESH STREAMING TABLE 1_bronze_db.orders_bronze AS
SELECT *, current_timestamp() AS processing_time,
       _metadata.file_name AS source_file
FROM STREAM read_files("{{ source_path }}/orders", format => 'JSON');

Silver: orders_silver

Lê do orders_bronze com o FROM STREAM.

CREATE OR REFRESH STREAMING TABLE 2_silver_db.orders_silver AS
SELECT order_id, timestamp(order_timestamp) AS order_timestamp,
       customer_id, notifications
FROM STREAM 1_bronze_db.orders_bronze;

Materialized view

Mantém resultados corretos com base no estado atual das streaming tables. Os pontos principais:

  1. Recálculo dinâmico: a cada atualização, a consulta é recalculada para refletir as mudanças a montante.
  2. Manutenção dirigida pelo pipeline: ela é criada e atualizada automaticamente.
  3. O comando é o CREATE OR REFRESH MATERIALIZED VIEW.
  4. Posicionamento flexível: pode ser usada em qualquer ponto do pipeline, não só no gold.
  5. Refresh incremental quando aplicável, evitando a reconstrução total (suportado em serverless).
  6. Otimização baseada em custo: um otimizador decide entre o refresh incremental e a recomputação completa.

Gold: gold_orders_by_date

CREATE OR REFRESH MATERIALIZED VIEW 3_gold_db.gold_orders_by_date AS
SELECT date(order_timestamp) AS order_date, count(*) AS total_daily_orders
FROM 2_silver_db.orders_silver
GROUP BY date(order_timestamp);

Diferença-chave: a fonte da MV vem sem a palavra STREAM. Ao contrário da streaming table, a MV gerencia seus próprios refreshes com base na origem.

Temporary Views e Views

As views são tabelas virtuais, que não armazenam dados físicos.

TipoCaracterísticas
Temporary ViewExiste só durante a execução do pipeline e não é registrada no Unity Catalog. Serve de camada SQL intermediária, para consultas internas
ViewÉ registrada no Unity Catalog e persiste depois da execução
 
CREATE TEMPORARY VIEW orders_active AS
SELECT * FROM 2_silver_db.orders_silver WHERE notifications = 'Y';

CREATE VIEW 3_gold_db.orders_active_view AS
SELECT * FROM 2_silver_db.orders_silver WHERE notifications = 'Y';

Limitações: o pipeline precisa ser um pipeline Unity Catalog. As views não podem ter consultas streaming nem ser a fonte streaming de um pipeline. A sintaxe não tem o OR REFRESH.

O que mudou de DLT para SDP

As palavras-chave antigas do Delta Live Tables (DLT) continuam aceitas por compatibilidade, mas pipelines novos devem usar a sintaxe nova.

Antiga (DLT)Moderna (SDP)
CREATE OR REFRESH STREAMING LIVE TABLECREATE OR REFRESH STREAMING TABLE
CREATE OR REFRESH LIVE TABLECREATE OR REFRESH MATERIALIZED VIEW
CREATE LIVE VIEW e CREATE TEMPORARY LIVE VIEWCREATE VIEW e CREATE TEMPORARY VIEW

Resolução automática de dependências

O SDP analisa as dependências automaticamente, então a ordem do código não importa. Tudo é conectado no Declarative Pipeline Graph, que garante o fluxo correto dos dados: o JSON bruto, o bronze (FROM STREAM read_files), o silver (FROM STREAM orders_bronze) e a materialized view (FROM orders_silver).

Conclusão

A lição revisou o projeto (uma arquitetura modular para ingerir, transformar, juntar e agregar dados de varejo), o papel de cada tipo de dataset (da ingestão contínua à agregação incremental e execução sob demanda) e a criação por SQL, de forma declarativa e consistente.

O que não li: as abas Step-2 e Step-3 do projeto, os passos 2 e 3 de cada camada de streaming table e os passos 2 a 4 da gold, as notas "Saiba mais" e os últimos itens da conclusão. Nada disso está nestas anotações.

O que guardar: a streaming table processa só os dados novos e usa o FROM STREAM. A materialized view recalcula (ou atualiza de forma incremental) sobre o estado atual e lê a origem sem o STREAM. A view não guarda dados, e a temporary não vai para o Unity Catalog. Não existe LIVE na sintaxe moderna. E a ordem do código não importa, porque o SDP monta o grafo de dependências sozinho.
