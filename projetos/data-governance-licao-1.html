Get Started with Data Governance on Databricks · Lição 1

Em desenvolvimento

Esta lição apresenta as bases do Unity Catalog: como ele entrega a governança unificada e aberta para todos os dados e ativos de IA, o papel do metastore, a hierarquia de objetos securáveis e a diferença entre as tabelas e volumes gerenciados e externos.

Estas anotações partem de um resumo da leitura da lição, não da lição inteira. Algumas partes não foram abertas, e isso está indicado no fim da página. A prática dos conceitos é a Demo 2.

Governança unificada e aberta

O Unity Catalog se destaca por oferecer a governança unificada e aberta para todos os dados e IA. Ele consolida quatro áreas em uma só camada:

Segurança

Acesso e auditoria

O controle de acesso e a auditoria.

Colaboração

Descoberta e compartilhamento

A descoberta e o compartilhamento seguro de dados.

Qualidade

Lineage e monitoramento

O lineage e o monitoramento de qualidade.

Gestão

Custos e semântica

O controle de custos e a semântica de negócio.

Ele governa todos os tipos de ativos (tabelas, modelos de IA, arquivos, notebooks e dashboards) e se baseia em padrões abertos: conecta-se a qualquer fonte externa e colabora com qualquer ferramenta, engine ou plataforma, sobre formatos abertos (Delta Lake, Parquet e Iceberg).

Unity Catalog open source

O controle centralizado vem junto com a abertura. O Unity Catalog é o catálogo universal para dados e IA ("qualquer engine, cliente, ativo e formato"), e suporta Delta Lake, Parquet, Apache Iceberg (e Hudi). A camada de governança central da versão open source expõe:

  • a Unity REST API;
  • a Iceberg REST catalog API;
  • o OpenSharing.

Entre o ecossistema de parceiros (as grandes clouds, as plataformas de dados e IA e as engines de compute, como Spark, DuckDB e Trino) e os ativos governados: tabelas (gerenciadas, externas e views), objetos (volumes, com imagem, áudio e PDF) e IA e ML (funções, modelos de ML e vector DBs). O resultado é a máxima interoperabilidade, sem lock-in.

Recursos para desenvolvedores

  • A gestão programática e a integração com o ecossistema: a especificação OpenAPI completa, o servidor OSS, as REST APIs e os SDKs (Java, Python e Go).
  • Recomenda-se integrar a administração do Unity Catalog a plataformas de infraestrutura como código, para implantações de segurança auditáveis e repetíveis.
  • O secure credential vending protege os tokens de acesso usados na integração com o cloud storage.

O metastore e a hierarquia de objetos securáveis

No topo está o metastore: o contêiner de topo e o ponto central de controle de acesso em uma região de nuvem. Ele também aplica a separação entre os metadados (no Control Plane) e os dados (no Cloud Storage). Em geral é criado pelo Account Administrator. Seus elementos são o acesso a storage externo, os catálogos, a Lakehouse Federation e o OpenSharing.

Funções governadas

Usa-se a sintaxe SQL nativa para registrar funções customizadas em schemas. As funções SQL ou Python são registradas e governadas pelo Unity Catalog, e exigem o privilégio CREATE FUNCTION no schema. As UDFs Python dão a expressividade para a lógica customizada (hashing condicional e redação complexa) que a conformidade, como o GDPR ou o HIPAA, pede.

O exemplo no Catalog Explorer é a função roll_dice: SCALAR, retorna INT, escrita em SQL e não determinística, com a definição (rand() * 6)::INT + 1, no schema psp_turbine_iot. São as mesmas UDFs que a Demo 4 usa nos row filters e column masks.

Modelos

O registro de modelos MLflow no Unity Catalog organiza os modelos por catálogo e schema, para uma gestão centralizada e entre workspaces.

  • Para registrar e gerenciar versões, são necessários USE CATALOG, USE SCHEMA e CREATE MODEL no schema.
  • Os donos criam as novas versões, e toda versão de modelo UC deve ter uma assinatura de modelo.
  • A integração permite que todo o ciclo de vida de IA seja auditável e governado em um só sistema.

O exemplo é o modelo dbdemos_turbine_maintenance, versão 1, com o alias @prod.

Conclusão

  • Unity Catalog: uma camada única, aberta e padronizada, sobre formatos e padrões abertos.
  • Metastore: o contêiner e o ponto de controle por região de nuvem, que separa os metadados (control plane) dos dados (cloud storage).
  • Hierarquia de objetos: o namespace de três níveis.
  • Gerenciado × externo: nos objetos gerenciados, o Unity Catalog é dono do ciclo de vida dos dados. Nos externos, os dados ficam em um local de nuvem gerenciado pelo cliente.

O que não li: os botões "Metastore Elements" e "Securable Object Hierarchy" do diagrama interativo (e os subcasos de Table e Volume), a seção de volumes e o início da seção de modelos. Por isso a lição, nestas anotações, quase não fala dos volumes gerenciados e externos, apesar de o objetivo citá-los.

O que guardar: o Unity Catalog é uma camada única e aberta de segurança, colaboração, qualidade e gestão. O metastore é o topo, por região, e separa os metadados dos dados. A hierarquia é catalog.schema.object. Em uma tabela gerenciada, o DROP TABLE apaga os dados (com o UNDROP como rede de segurança), e em uma externa só os metadados. Funções e modelos também são objetos governados, e pedem CREATE FUNCTION e CREATE MODEL no schema.
