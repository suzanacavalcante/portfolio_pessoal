Powering Downstream Analytics in Snowflake using UC Managed Tables

Data Interoperability with Unity Catalog · Demo 2

Em desenvolvimento

Esta demo, de cerca de 9 minutos, expõe ao Snowflake as tabelas da demo anterior (a Iceberg gerenciada e a Delta com UniForm), como motor analítico downstream. O caminho é o endpoint Iceberg REST do Unity Catalog e uma catalog integration do Snowflake. No fim, um analista do Snowflake faz um join em uma única consulta entre a tabela fato (no Unity Catalog) e uma dimensão (no Snowflake), sem copiar dados.

Estas anotações partem de um resumo da demo, não da transcrição. Segundo o resumo, a única legenda do vídeo está em chinês simplificado, e o resumo foi feito a partir dela. O SQL que aparece é um esboço meu, com marcadores no lugar dos valores, e não foi executado. A sintaxe exata deve ser conferida na documentação dos dois produtos.

Objetivo e pré-requisitos

As tabelas são a store_sales_iceberg e a store_sales_delta_uniform, criadas na demo anterior. O Unity Catalog continua sendo a autoridade de governança (as permissões, o lineage e a auditoria).

  • Acesso em nível de conta nas duas plataformas: metastore admin ou account admin no Databricks, e account admin no Snowflake.
  • Uso de armazenamento gerenciado pelo cliente. Não funciona com o storage serverless gerenciado pela Databricks.

A arquitetura

No Snowflake, a catalog integration autentica via OAuth como service principal e cria referências a tabelas Iceberg. O analista consulta essas referências, e os dados são lidos direto do storage do Unity Catalog com credenciais distribuídas (vended).

As verificações iniciais: as duas tabelas existem (uma Delta gerenciada e uma Iceberg gerenciada) e têm 1 milhão de linhas cada. O primeiro passo de setup é habilitar o external data access no metastore (Catalog Explorer, a engrenagem e Metastore). Já estava ligado.

Service principal e permissões (Databricks)

  • O service principal é a identidade com que o Snowflake se autentica. O Snowflake guarda credenciais OAuth, não tokens de usuário. Ele pode ser criado por SDK, API ou infraestrutura como código. Aqui já existia (Snowflake Integration, em Account Console, User Management e Service Principals).
  • Guarda-se o application ID (um UUID), usado na catalog integration e nos GRANTs, e o OAuth secret (só o secret ID é visível).
  • O service principal existe no nível da conta e não é membro de nenhum workspace. Precisa ser adicionado ao workspace de destino, em Permissions.

Cuidado com o secret: trate o OAuth secret como segredo. Não o versione, e use um gerenciador de segredos.

As permissões no Unity Catalog, em ordem:

  1. EXTERNAL USE SCHEMA no schema: permite o acesso via Iceberg REST. Sem ele, o acesso só seria interno.
  2. Os privilégios padrão: USE CATALOG, USE SCHEMA e SELECT nas duas tabelas.

No GRANT, o principal é identificado pelo application ID. Depois, os grants são conferidos com o SHOW GRANTS.

-- esboço meu, com marcadores no lugar dos valores
GRANT EXTERNAL USE SCHEMA ON SCHEMA <catalogo>.<schema> TO `<application-id>`;
GRANT USE CATALOG ON CATALOG <catalogo> TO `<application-id>`;
GRANT USE SCHEMA ON SCHEMA <catalogo>.<schema> TO `<application-id>`;
GRANT SELECT ON TABLE <catalogo>.<schema>.store_sales_iceberg TO `<application-id>`;
GRANT SELECT ON TABLE <catalogo>.<schema>.store_sales_delta_uniform TO `<application-id>`;

Catalog integration (Snowflake)

Já como account admin no Snowflake, cria-se uma catalog integration, que é uma referência nomeada a um catálogo Iceberg externo. Ela empacota a URI do endpoint REST, as credenciais OAuth e o modo de distribuição de credenciais.

  • A catalog URI e a OAuth token URI usam o nome de deployment do workspace.
  • O client ID é o ID do service principal (o client ID e o secret aparecem tarjados no vídeo).
  • O access delegation é configurado como credenciais distribuídas: o Unity Catalog entrega ao Snowflake credenciais de curta duração, em vez de ele manter credenciais de longa duração.

Verifica-se com o SHOW CATALOG INTEGRATIONS e o DESCRIBE.

Tabelas Iceberg no Snowflake

Cada tabela Iceberg no Snowflake é uma referência à tabela do Unity Catalog, acessada pela catalog integration: nenhuma cópia dos dados, só metadados. Os comandos apontam o CATALOG para a integration criada e usam o auto-refresh = true, para o Snowflake reconsultar o Unity Catalog e atualizar os metadados no intervalo configurado.

Consultas e conclusões

  1. Smoke test: 1 milhão de linhas nas duas tabelas, igual ao Unity Catalog, e o DESCRIBE TABLE mostra as colunas.
  2. Join: entre a tabela fato do Unity Catalog e a dimensão do Snowflake (com uma CTE de datas de exemplo), com sucesso.
AspectoOnde acontece
Cópia de dadosNenhuma, em nenhum dos lados
Compute da consultaInteiro no Snowflake
Governança e gestão das tabelasNo Unity Catalog

Ligação com o treinamento anterior: o EXTERNAL USE SCHEMA é mais um privilégio na cadeia que a lição Privileges in Unity Catalog descreve (USE CATALOG, USE SCHEMA e SELECT), e o service principal é um dos principais da ACL. A ligação é minha.

O que guardar: para o Snowflake ler as tabelas do Unity Catalog sem copiar os dados, são necessários: o external data access habilitado no metastore, um service principal (adicionado ao workspace) com EXTERNAL USE SCHEMA, USE CATALOG, USE SCHEMA e SELECT, e uma catalog integration no Snowflake, com credenciais distribuídas de curta duração. As tabelas ficam como referências, com auto-refresh. O compute roda no Snowflake, e a governança continua no Unity Catalog.
