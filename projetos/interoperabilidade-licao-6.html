Centralized Data Processing with External Analytics

Data Interoperability with Unity Catalog · Lição 6

Em desenvolvimento

Esta lição, do Módulo 3 (casos de uso de interoperabilidade), apresenta o primeiro grande caso de uso: usar a Databricks como hub central de processamento, enquanto engines analíticos externos (Snowflake e Trino) leem as mesmas tabelas governadas pelo Unity Catalog, por credential vending e pelo Iceberg REST Catalog.

Estas anotações partem de um resumo da leitura da lição. Segundo o resumo, a lição foi lida por completo, mas o bloco "Show Sequence Diagram" da seção de implementação abriu sem conteúdo visível, e por isso ele não está resumido. A prática é a Demo 2, com o Snowflake.

O contexto

A Databricks ingere e transforma os dados em um só lugar, e o Unity Catalog governa esses dados para os consumidores nativos e externos. O fluxo do diagrama da lição:

  • Usar a Databricks como hub central, com o Unity Catalog como a fonte da verdade.
  • Permitir que engines externos façam o processamento downstream.
  • Manter a governança centralizada ao permitir o acesso externo.

O detalhe de implementação

O fluxo de dados combina a ingestão, a transformação e o consumo externo em uma única sequência, governada ponta a ponta pelo Unity Catalog: da ingestão na fonte até os clientes externos lendo pelo endpoint Iceberg REST.

O fluxo de credential vending

Antes de um cliente externo ler uma tabela do Unity Catalog pelo endpoint Iceberg REST, ele troca a sua identidade por uma credencial de storage curta e restrita ao caminho, emitida pelo Unity Catalog. O Unity Catalog também grava um registro de auditoria no momento da autorização. Assim, o "quem tocou em quê" é capturado no plano de controle, e não no plano de dados. O handshake completo está na lição External Access to Managed Tables.

A implementação de referência: lendo dados do Unity Catalog no Snowflake

Pré-requisito: um usuário ou service principal com o papel Account Admin habilitado, e um papel igualmente privilegiado no sistema externo.

LadoPassos
Databricks
  1. Habilitar o External Data Access: ligar o acesso externo Iceberg REST no nível do metastore.
  2. Criar as tabelas gerenciadas: como Iceberg gerenciada ou Delta com UniForm.
  3. Criar uma service principal, com um client secret para o engine externo se autenticar.
  4. Conceder os privilégios: EXTERNAL USE SCHEMA, SELECT e USE no catálogo e no schema, para a service principal.
Snowflake
  1. Criar a Catalog Integration: CREATE CATALOG INTEGRATION, com as credenciais da service principal e a URL do endpoint Iceberg REST do Unity Catalog.
  2. Criar as tabelas Iceberg: CREATE ICEBERG TABLE, referenciando a catalog integration.
  3. Consultar nativamente: o SELECT nas tabelas Iceberg, como em qualquer tabela do Snowflake.

Outros sistemas: o mesmo padrão vale para o Trino, o Dremio, o Starburst e outros engines compatíveis com o Iceberg. Cada sistema tem a sua própria sintaxe de catalog integration.

Ligação com a Demo 2: os passos acima são, na ordem, os da Demo 2: o external data access no metastore, a service principal (Snowflake Integration), os grants (EXTERNAL USE SCHEMA, USE CATALOG, USE SCHEMA e SELECT), a catalog integration e as tabelas Iceberg como referências. A ligação é minha.

Key Takeaways

  • O processamento centralizado mantém a governança unificada e permite um analytics flexível.
  • O credential vending dá acesso seguro e com tempo limitado a sistemas externos.
  • O Iceberg REST Catalog é o ponto de integração para os engines analíticos externos.
  • A implementação exige service principals com os privilégios corretos no Unity Catalog.

O que guardar: neste caso de uso, a Databricks processa e o Unity Catalog governa. Os engines externos (Snowflake, Trino e outros) só leem, pelo Iceberg REST, cada um com a sua service principal e com credenciais curtas. Para habilitar: o external data access no metastore, as tabelas gerenciadas (Iceberg ou Delta com UniForm), a service principal com os grants e, no engine externo, a catalog integration e as tabelas Iceberg.
