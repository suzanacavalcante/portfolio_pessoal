Lakehouse Federation Overview

Data Interoperability with Unity Catalog · Lição 8

Em desenvolvimento

Esta lição abre o Módulo 5 (Lakehouse Federation). Ela apresenta a federação no Unity Catalog e distingue as suas duas formas: a catalog federation (espelha um metastore legado) e a lakehouse federation (expõe um banco externo no próprio local). As duas se constroem sobre as mesmas primitivas: connection e foreign catalog.

Estas anotações partem de um resumo da leitura da lição. Segundo o resumo, a lição foi lida por completo (a página não tinha blocos expansíveis), e os links dela apontam para as lições 5.2 a 5.5 do próprio curso. A prática são as Demos 4, 5 e 6.

O que é a Lakehouse Federation

É um termo guarda-chuva para os recursos do Unity Catalog que permitem consultar dados que vivem fora dele como se fossem um ativo seu, sem copiar ou mover os dados.

Os dois blocos de construção, comuns às duas formas:

  • Connection: guarda as credenciais e a configuração da fonte externa.
  • Foreign Catalog: espelha o namespace da fonte dentro do Unity Catalog.

Catalog federation × lakehouse federation

Elas diferem no que é federado: a catalog federation aponta para outro metastore, e a lakehouse federation aponta para outro banco de dados.

Catalog federation: a ponte para metastores legados

É usada principalmente para migrar de um Hive Metastore ou de um catálogo AWS Glue legado para o Unity Catalog sem interromper as cargas que já rodam sobre essas tabelas. O caminho típico de adoção:

  1. Registrar o metastore legado como um foreign catalog: as tabelas existentes ficam consultáveis pelo Unity Catalog imediatamente.
  2. Os workloads passam gradualmente a ler pelo Unity Catalog, ganhando a governança dele.
  3. As tabelas são migradas no local, de foreign para external e depois para managed.
  4. Com todas as tabelas migradas, o foreign catalog pode ser aposentado.

Lakehouse federation: juntando bancos externos

Expõe um banco externo "vivo" pelo Unity Catalog, para consultar e fazer join dos dados no local. Os predicados, as projeções e as agregações suportados são empurrados (pushdown) para a fonte. Os casos de uso típicos:

  • juntar dados operacionais do PostgreSQL, do MySQL ou do SQL Server com dados analíticos do lakehouse, sem ETL;
  • ler de outro data warehouse (Snowflake, Redshift ou BigQuery) sob a governança do Unity Catalog;
  • expor dados OLTP no Lakebase (o PostgreSQL gerenciado pela Databricks) para as cargas do lakehouse.

O comportamento de pushdown

O desempenho da lakehouse federation depende muito do que o Unity Catalog consegue empurrar para a fonte, em vez de trazer linhas para a Databricks.

PushdownNormalmente suportado
Filtros, projeções e limitsTodas as fontes
Agregações e operadores aritméticosA maioria das fontes, em DBR 13.3 LTS ou superior e em SQL Warehouses
Ordenação (com limit)A maioria das fontes, em DBR 13.3 LTS ou superior e em SQL Warehouses
JoinsEm DBR mais novo (por exemplo, o PostgreSQL exige DBR 17.2 ou superior, ou SQL Warehouses 2025.30 ou superior)
Window functionsGeralmente não são empurradas

Os detalhes variam por fonte. O lab 5.5 mostra como ler a saída do EXPLAIN para confirmar o que foi empurrado em uma consulta federada ao PostgreSQL, que é o que a Demo 6 faz com o EXPLAIN FORMATTED.

Key Takeaways

  • A Lakehouse Federation cobre dois padrões distintos, construídos sobre as mesmas primitivas: connection e foreign catalog.
  • A catalog federation aponta o Unity Catalog para outro metastore (HMS e Glue), tipicamente uma ponte de migração.
  • A lakehouse federation aponta o Unity Catalog para outro banco (PostgreSQL/Lakebase, SQL Server, Snowflake e outros), tipicamente uma integração de longa duração.
  • As duas mantêm os dados no lugar: as credenciais e a configuração ficam na connection, e o namespace no foreign catalog.
  • O pushdown determina o desempenho da federação de lakehouse, e se verifica com o EXPLAIN.

O que guardar: a pergunta é "o que estou federando?". Um metastore (Hive ou Glue) é catalog federation, uma ponte de migração: foreign, depois external, depois managed. Um banco (PostgreSQL, SQL Server, Snowflake e outros) é lakehouse federation, e os dados ficam na fonte. A infraestrutura é a mesma, connection e foreign catalog, e o desempenho depende do pushdown, conferido pelo EXPLAIN.
