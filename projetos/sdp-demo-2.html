Developing a Simple Pipeline

Build Data Pipelines with Lakeflow Spark Declarative Pipelines · Demo 2

Em desenvolvimento

Esta demo, de cerca de 20 minutos, migra o ETL tradicional de orders para um pipeline SDP. Ela usa streaming tables, em SQL, nas camadas bronze e silver, e uma materialized view na gold. Depois, configura o pipeline com uma variável source e o executa, mostrando a ingestão incremental, o dry run e o full table refresh.

Estas anotações partem de um resumo cronometrado da demo, não da transcrição. O código é um exemplo escrito por mim a partir desse resumo, com nomes genéricos (só o orders_bronze_demo aparece no resumo), e não foi executado.

Preparação e criação do pipeline

O ponto de partida é um notebook em serverless v5, com o classroom setup e uma célula que fornece o valor (o caminho do volume) a copiar para a configuração do pipeline. Para criar o pipeline:

  1. No menu Jobs & Pipelines (em uma nova aba), cria-se um novo ETL pipeline.
  2. Renomeia-se para "05-Developing a Simple Pipeline", e a pasta raiz do pipeline também é renomeada.
  3. Seleciona-se o catálogo e o schema padrão (sdp_1_bronze).
  4. Renomeia-se a pasta de transformações para orders e o arquivo para orders_pipeline.sql. Pode-se ter quantos notebooks, arquivos Python ou queries forem necessários.

O código

Bronze

Streaming table

Um CREATE OR REFRESH STREAMING TABLE, que é uma tabela Delta com capacidade de streaming. Lê com a read_files no caminho ${source}/orders, com a palavra-chave STREAM, e inclui metadados.

Silver

Streaming table

Também streaming, com transformações leves (escolher colunas, rotular e fazer cast). Lê do orders_bronze com o STREAM no FROM.

Gold

Materialized view

Agrega por data, com o total_daily_orders.

CREATE OR REFRESH STREAMING TABLE sdp_1_bronze.orders_bronze_demo AS
SELECT
    *,
    current_timestamp() AS processing_time,
    _metadata.file_name AS source_file
FROM STREAM read_files('${source}/orders', format => 'json');

CREATE OR REFRESH STREAMING TABLE orders_silver_demo AS
SELECT
    order_id,
    CAST(order_timestamp AS TIMESTAMP) AS order_timestamp,
    customer_id,
    notifications
FROM STREAM(orders_bronze_demo);

CREATE OR REFRESH MATERIALIZED VIEW orders_by_date AS
SELECT date(order_timestamp) AS order_date, count(*) AS total_daily_orders
FROM orders_silver_demo
GROUP BY date(order_timestamp);
  • O nome qualificado (sdp_1_bronze.orders_bronze_demo) define onde a tabela vai. Sem qualificar, ela vai para o catálogo e o schema padrão.
  • A variável ${source} é substituída em tempo de execução pelo valor da configuração.

Atenção: esquecer o STREAM pode deixar os dados desatualizados.

Dry run e execução

O Dry Run, no dropdown do botão azul, valida o código, os catálogos e os schemas sem criar nem atualizar tabelas e sem fluir dados. Ele mostra o preview dos datasets (o bronze, o silver e a MV orders_by_date) e a linhagem.

Por padrão, o SDP roda com processamento incremental. O volume tem um único JSON, com 174 registros. Ao rodar o pipeline (Run pipeline), o pipeline graph mostra o fluxo: o bronze leva cerca de 15 segundos (174 registros), o silver cerca de 3 segundos (174 registros), e a MV mostra seus registros de saída.

As abas de saída reúnem tudo em um só lugar:

  • Tables: duração, registros de saída e expectations;
  • Performance: os statements SQL, as linhas e os bytes lidos e escritos, e o query profile ao clicar;
  • a navegação pelo graph para ver os dados de cada tabela.

Execução incremental

ExecuçãoO que aconteceu
1ªCarga inicial de 174 registros no bronze e no silver
2ª, sem novos arquivosO Auto Loader garante a idempotência por arquivo, então as streaming tables têm 0 registros de saída. A MV é atualizada (saída de 7)
3ª, com um novo arquivoUma célula do notebook adiciona JSONs à pasta orders, agora com 2 arquivos. O Auto Loader acrescenta cerca de 25 registros ao bronze, e o silver processa os novos. A MV usa o refresh incremental, só com os novos dados, e não com o silver inteiro, por estar em serverless. O bronze totaliza 199 (174 + 25), e a MV ganha um novo agregado, a data de 1º de janeiro de 2022, com o rótulo "incremental"

Full table refresh

É o modo que trunca todas as tabelas do pipeline e reprocessa tudo do zero. Na demo, ele reprocessa cerca de 199 registros, lendo os dois arquivos.

Cuidado em produção: em desenvolvimento, o full refresh é aceitável. Em produção, ele apaga os dados já processados e pode causar perda de dados.

O que guardar: a migração do ETL tradicional para o SDP troca o CREATE OR REPLACE TABLE por CREATE OR REFRESH STREAMING TABLE no bronze e no silver, com o STREAM na leitura, e por uma materialized view na gold. A variável source vem da configuração do pipeline. O dry run valida sem mexer nos dados, a execução é incremental por padrão, e o Auto Loader evita reprocessar arquivos já lidos. A MV também é atualizada de forma incremental no serverless. O full table refresh apaga e reprocessa tudo, e pede cuidado em produção.
