Adding Data Quality Expectations

Build Data Pipelines with Lakeflow Spark Declarative Pipelines · Demo 3

Em desenvolvimento

Esta demo, de cerca de 9 minutos, estende o pipeline de orders com expectations, que são restrições de qualidade de dados. A camada silver ganha três delas, uma para cada ação possível: avisar (warn), descartar o registro (drop) e falhar a atualização (fail).

Estas anotações partem de um resumo cronometrado da demo, não da transcrição. O código é uma reconstrução minha a partir desse resumo e não foi executado.

Preparação e criação do pipeline por código

O ponto de partida é um notebook em serverless v5. O classroom setup fornece recursos, variáveis e funções, e uma célula obtém o caminho do volume com os JSONs de orders.

Desta vez o pipeline não é criado pela UI. Uma célula chama a função create_declarative_pipeline, fornecida pelo setup, que usa a API para criar o objeto do pipeline. Isso é útil ao promover um pipeline entre ambientes. O pipeline "07-Adding Data Quality Expectations" nasce com pasta raiz, catálogo e schema padrão e os code assets na pasta orders.

As expectations

O bronze não mudou. Na silver, logo depois do CREATE OR REFRESH STREAMING TABLE, entram as constraints. Cada uma tem um nome customizado, a palavra EXPECT e uma avaliação booleana:

Warn

valid_notification

A coluna notifications só pode ter os valores Y e X. Sem ação definida, o padrão é warn: só registra a violação, e o registro segue para a tabela.

Drop

valid_date

O order_timestamp tem de ser posterior a 26/12/2021, com ON VIOLATION DROP ROW, que descarta o registro.

Fail

valid_id

O customer_id não pode ser nulo, com ON VIOLATION FAIL UPDATE, que faz a atualização falhar.

CREATE OR REFRESH STREAMING TABLE orders_silver_demo (
    CONSTRAINT valid_notification EXPECT (notifications IN ('Y', 'X')),
    CONSTRAINT valid_date EXPECT (order_timestamp > '2021-12-26') ON VIOLATION DROP ROW,
    CONSTRAINT valid_id EXPECT (customer_id IS NOT NULL) ON VIOLATION FAIL UPDATE
) AS
SELECT
    order_id,
    CAST(order_timestamp AS TIMESTAMP) AS order_timestamp,
    customer_id,
    notifications
FROM STREAM(orders_bronze_demo);

O conteúdo da tabela continua o mesmo, e a materialized view também. O que muda é o que acontece com os registros que violam as regras.

Observação: os dados têm o valor "N" em notifications. O exemplo foi ajustado de propósito para que a expectation valid_notification disparasse o aviso.

  • O painel lateral, ao clicar na tabela, mostra 148 registros escritos (85%) e 26 descartados (14,9%), e um toggle para ver todas as expectations. Ali se confirma que não há cliente nulo.
  • Na aba Tables, a coluna de expectations mostra "1 met, 2 unmet", e clicar abre o mesmo painel.
  • Na orders_silver_demo, as notificações têm os valores Y e O, porque a regra foi alterada para X. Os registros com "N" violam a expectation.

Ponto a conferir: o resumo diz que a regra aceita Y e X, e depois que as notificações da tabela têm Y e O "porque a regra foi alterada para X". Não ficou claro para mim qual valor a tabela realmente tem, então no código acima usei Y e X, como na descrição da regra. Vale conferir no vídeo.

Os três níveis

AçãoSintaxeEfeito
Warnsó o EXPECT (padrão)Registra a violação e mantém o registro
DropON VIOLATION DROP ROWDescarta o registro que viola
FailON VIOLATION FAIL UPDATEInterrompe o pipeline, e exige intervenção manual

As expectations servem para campos obrigatórios, faixas válidas e regras de negócio, para remover registros ruins e proteger datasets críticos, e para monitorar a qualidade e as tendências ao longo do tempo.

O que guardar: uma expectation é uma constraint com nome, EXPECT e uma condição booleana, escrita logo depois do CREATE OR REFRESH STREAMING TABLE. Sem ação, ela só avisa (warn). Com DROP ROW, descarta o registro. Com FAIL UPDATE, derruba a atualização. As métricas aparecem no graph (quadrado para descartados, triângulo para avisos) e na aba Tables. Arquivos de exploração, com a corrente quebrada, não entram na execução do pipeline.
