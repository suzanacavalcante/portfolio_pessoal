Implementing Fine-Grained Access Controls

Get Started with Data Governance on Databricks · Demo 4

Em desenvolvimento

Esta demo, de cerca de 31 minutos, implementa o controle de acesso refinado de três formas: o DDL SQL nativo (row filters e column masks, com funções reutilizáveis), as dynamic views (uma técnica alternativa) e o ABAC, com políticas baseadas em governed tags. No fim, compara as abordagens e depura erros comuns de permissão.

Estas anotações partem de um resumo cronometrado da demo, não da transcrição. O SQL que aparece é um esboço meu, a partir do que o resumo descreve, e não foi executado. Os nomes dos grupos e das regiões nas funções são suposições minhas.

O que a demo faz

Cria o schema HR com dados sensíveis, aplica filtros de linha e máscaras de coluna, constrói views seguras com a mesma lógica, compara com o modelo nativo e depura os erros de permissão. Os requisitos são os mesmos da demo anterior: o Unity Catalog, o Databricks Runtime 17.3 LTS ou superior (ou serverless v4 ou superior) e os privilégios de criar e usar catálogo, schema e tabela.

Setup

O setup usa o serverless e reaproveita, em segundos, os objetos da demo anterior (ou os cria em 3 a 4 minutos, com um job Lakeflow). O objeto DA guarda o usuário, o catálogo, o catálogo office, o warehouse (nome e ID) e o secondary principal (nome e client ID), que serve para testar as permissões de outro usuário.

A função is_account_group_member verifica a participação em grupos de conta, para uma segurança condicional (testada com Users, users e admin).

Construindo os dados

  • As governed tags (PII, classification e geo_access) são de nível de conta, com valores permitidos. Aqui só são referenciadas: PII (SSN e email) nas colunas, e geo_access = region_filter na coluna de região. Essas tags serão os "interruptores" das políticas ABAC.
  • Cria-se e tagueia-se o catálogo db_office_<usuário> e o schema HR, definidos como padrão.
  • As tabelas employees (dados sensíveis) e employee_benefits recebem tags descritivas e dados de teste.

Detalhe da tag: usa-se contains_pii = true (uma tag livre) porque a PII é governada e não aceita valores arbitrários pelo set tags. Ela precisa ser atribuída em uma coluna, com ALTER TABLE ... ALTER COLUMN ... SET TAGS e um valor permitido (SSN, email ou address).

Grants para o secondary principal

O Unity Catalog usa um modelo de permissão explícito: nada é implícito nem herdado dos contêineres. Para acessar um objeto é preciso USE CATALOG e USE SCHEMA nos contêineres, mais o privilégio no objeto (SELECT na tabela).

Concede-se a cadeia (catálogo, schema e SELECT só na employees), e células inline conectam um cliente SQL como o secondary principal. O resultado:

  • ele consegue consultar a employees;
  • a consulta à employee_benefits falha, porque ele nunca recebeu a permissão.

O princípio é que as permissões são aplicadas por tabela ou view. O acesso a uma tabela não dá acesso às outras do mesmo schema.

Fine-grained nativo

São dois passos: escrever uma UDF reutilizável com a lógica de segurança, e anexá-la à tabela. Como a lógica fica na função, aplicada na tabela de origem, a abordagem escala bem.

MecanismoComo funcionaAplicação
Row filterA função retorna um predicado booleano, que decide as linhas visíveisALTER TABLE ... SET ROW FILTER
Column maskA função retorna o dado em claro só para quem tem o privilégioALTER COLUMN ... SET MASK

As funções criadas na demo:

  • redact_ssn: a redação total do SSN, com o HR vendo o valor completo;
  • a máscara de e-mail: um regex que ofusca parcialmente;
  • redact_salary: o salário visível só para o HR;
  • filter_region: o HR vê todas as regiões, e os demais veem apenas a Americas.
-- esboço meu: o grupo 'HR' e a região 'Americas' vêm do resumo, o resto é suposição
CREATE FUNCTION redact_ssn(ssn STRING)
RETURN IF(is_account_group_member('HR'), ssn, '***-**-****');

CREATE FUNCTION filter_region(region STRING)
RETURN IF(is_account_group_member('HR'), true, region = 'Americas');

ALTER TABLE employees ALTER COLUMN ssn SET MASK redact_ssn;
ALTER TABLE employees SET ROW FILTER filter_region ON (region);

Dynamic views

Em vez de impor a política na tabela, a view fica sobre os dados e embute a lógica de máscara e de filtro. É flexível, mas exige uma view por padrão de acesso. Criam-se duas:

  • employees_secure, com as máscaras;
  • employees_multi_secure, com as máscaras e o row filter por filter_region.

O SELECT é concedido ao secondary principal. No teste, o usuário atual vê o SSN, o e-mail e o salário mascarados e, na multi-secure, só as linhas das Américas. O secondary principal (HR) vê tudo.

Comparação: a Databricks recomenda a segurança nativa de linha e de coluna, e não as dynamic views. Ela é aplicada na tabela de origem, com melhor desempenho, manutenção e escala, e sem objetos extras. As dynamic views ainda têm o seu lugar, mas cada padrão exige outra view.

Inspeção de funções e permissões

Examinam-se as funções redact_salary e filter_region e as permissões: a employees_secure tem SELECT para o service principal, e a employee_benefits não retorna nada, porque não tem grants.

ABAC

O ABAC move a governança dos DDLs pontuais para políticas definidas de forma central:

  • elas vivem em catálogos, schemas ou tabelas e são herdadas para baixo;
  • têm como alvo principais (usuários, grupos e service principals);
  • aplicam-se dinamicamente, conforme as governed tags dos objetos;
  • há hoje dois tipos, o row filter e o column mask;
  • só os donos, ou quem tem MANAGE, podem aplicá-las.

Reaproveitam-se as mesmas UDFs, sem alterar a definição da tabela:

PolíticaO que faz
HR mask SSNAssocia a redact_ssn à coluna SSN da employees, avaliada em runtime, sem o ALTER TABLE SET MASK
HR region filterReutiliza a filter_region na coluna de região. O usuário atual vê só as Americas, e o secondary principal vê todas as regiões. É o equivalente a um row filter de tabela, agora como política de schema

Depois, as duas políticas são removidas, para restaurar o acesso.

Ponto a conferir: este resumo não traz a sintaxe de criação das políticas ABAC. O resumo da Demo 3 só cita um exemplo, o SET RULE ... COLUMN MASK ... WHEN column tagged as PII. Por isso não escrevi esse SQL aqui. Vale conferir no vídeo e na documentação.

Erros comuns de permissão

Os testes usam uma função helper do setup. O acesso à view employees_secure funciona, e o acesso a uma tabela employees antiga retorna not found quando não há acesso. Revoga-se o SELECT do usuário atual na employees, e o teste como secondary principal mostra o erro, sem acesso.

Limpeza e conclusão

O run_destroy_pipeline (o job destroy_batch_jobs_demo_5, com 12 tasks tolerantes a falha) remove o catálogo, o schema, as tabelas, as UDFs, as views seguras e as políticas. Segundo o resumo, por ser a última demo, recomenda-se executá-lo para liberar o storage, acompanhando em Jobs & Pipelines.

Os dados sensíveis de HR foram protegidos de quatro formas, todas validadas consultando como o usuário atual e como o secondary principal:

AbordagemCaracterísticas
Row filter com UDFUm predicado booleano (por exemplo, filter_region)
Column maskredact_ssn, redact_email e redact_salary, condicionais à identidade
Dynamic viewsFlexíveis, mas uma view por padrão de acesso
ABACPolíticas de schema que aplicam máscaras e filtros pelas governed tags, sem DDL por objeto

O que guardar: as permissões do Unity Catalog são explícitas e por objeto, e é preciso USE CATALOG e USE SCHEMA além do SELECT. O row filter e o column mask nativos usam uma UDF anexada à tabela, e é o recomendado. As dynamic views dão o mesmo resultado com uma view por padrão. O ABAC move a regra para uma política central, herdada e guiada pelas governed tags (PII, geo_access), reaproveitando as mesmas funções.
