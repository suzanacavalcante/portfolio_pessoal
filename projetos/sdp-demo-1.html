Course Setup and Creating a Pipeline

Build Data Pipelines with Lakeflow Spark Declarative Pipelines · Demo 1

Em desenvolvimento

Esta demo, de cerca de 17 minutos, percorre o workspace e os recursos do curso e constrói um pipeline ETL tradicional como linha de base. Isso serve para mostrar os limites dessa abordagem e introduzir os Spark Declarative Pipelines (SDP), antes de criar o primeiro pipeline e conhecer a interface do editor.

Estas anotações partem de um resumo cronometrado da demo, não da transcrição. Os trechos de código são exemplos escritos por mim a partir desse resumo, com caminhos genéricos, e não foram executados. O diagrama do editor também é meu.

Preparação do ambiente

  • Conecta-se o notebook a um compute serverless, versão 5.
  • A célula de classroom setup cria os catálogos, schemas, volumes e arquivos usados no curso e imprime as variáveis.
  • No Catalog Explorer aparecem os schemas bronze, silver e gold (por exemplo, sdp_1_bronze). Dentro do bronze há um volume source, com JSONs de customers, orders e status.
  • Duas variáveis de caminho, uma registrada em Python e outra em SQL, apontam para o mesmo volume source.

Explorando os dados

Com o spark.sql(...) e um SELECT * FROM json usando o caminho do volume, lê-se o orders: cerca de 174 registros, com customer_id, notifications, order_id e order_timestamp.

O pipeline ETL tradicional

Um script com CREATE OR REPLACE TABLE constrói as três camadas:

ObjetoO que faz
orders_bronzeUsa a read_files sobre o caminho do volume e traz todas as colunas, mais metadados de tempo de processamento e do arquivo de origem
orders_silverLê do bronze, seleciona colunas, faz cast e adiciona um rótulo
orders_by_date (view)Agrega o total_daily_orders, agrupando por data
 
CREATE OR REPLACE TABLE orders_bronze AS
SELECT
    *,
    current_timestamp()      AS processing_time,
    _metadata.file_name      AS source_file
FROM read_files('caminho_do_volume/orders', format => 'json');

CREATE OR REPLACE TABLE orders_silver AS
SELECT
    order_id,
    CAST(order_timestamp AS TIMESTAMP) AS order_timestamp,
    customer_id,
    notifications
    -- a demo também adiciona uma coluna de rótulo
FROM orders_bronze;

CREATE OR REPLACE VIEW orders_by_date AS
SELECT date(order_timestamp) AS order_date, count(*) AS total_daily_orders
FROM orders_silver
GROUP BY date(order_timestamp);

Na verificação, o bronze traz a _rescued_data e as duas colunas extras. O silver tem order_id, order_timestamp (como timestamp), customer_id e notifications. A view mostra as contagens por data. O código funciona, mas não escala bem.

Os problemas do ETL tradicional

#Problema
1O bronze relê tudo a cada execução (leitura estática completa): o custo cresce com o total de arquivos, e não com os dados novos
2O silver reprocessa todas as linhas do bronze, sempre
3As views reexecutam a cada chamada, por serem uma consulta salva, o que lentifica os dashboards
4A qualidade de dados exige código extra (WHERE, CASE, asserts) fora do pipeline, e é fácil de esquecer
5O monitoramento existe só no nível do job (sucesso ou falha), e não do dado: quantos registros, duplicatas, falhas de parse
6Não há UI para explorar e corrigir: sem linhagem, preview ou visão do fluxo, e às vezes é preciso reexecutar tudo

"Dá para usar Structured Streaming?"

O Structured Streaming resolve o reprocessamento, mas exige reescrever com mais código e mais operação:

  • gerenciar os checkpoints, com um caminho persistente por stream;
  • fazer upserts, que não são simples: é preciso o foreachBatch, uma view temporária e um MERGE manual;
  • configurar o trigger e o schema location do Auto Loader;
  • controlar o ciclo de vida: start, stop e await.

Os erros geram falhas silenciosas ou streams que nunca terminam. E, ainda assim, não há restrições de qualidade, UI nem linhagem.

O que os SDP oferecem

Ingestão

Ingestão eficiente

Batch, streaming e CDC, sobre o Apache Spark.

Transformação

Transformação inteligente

Uma abstração sobre o Structured Streaming: poucas linhas de código, e o framework escolhe a estratégia de execução (batch ou streaming) e otimiza custo e desempenho sem ajuste manual.

Operação

Operações automatizadas

Gestão de dependências, escala, recuperação e aplicação de qualidade, sem infraestrutura para gerenciar.

Ao converter o batch, o resultado é o processamento incremental, a qualidade de dados, a infraestrutura gerenciada e a visibilidade completa do pipeline. Não há foreachBatch, checkpoints nem trigger manual.

Como criar um pipeline

  1. Pelo workspace: no menu de ações da pasta, Create → ETL pipeline, que cria um pipeline vazio.
  2. Pelo menu Jobs & Pipelines (ou pelo botão azul), com três opções: Ingestion pipeline (os conectores gerenciados do Lakeflow), ETL pipeline (os Spark Declarative Pipelines) e Lakeflow Jobs.

O editor de pipelines

O editor atende quatro preocupações de quem trabalha com engenharia de dados:

  1. Nome e arquivos: sempre há uma root folder associada ao pipeline, com um toggle para focar só nela ou ver todos os arquivos do workspace.
  2. Código: uma área que se comporta como um notebook ou arquivo comum.
  3. Saída e detalhes: a aba inferior, com as tabelas de saída, a performance e o pipeline graph, a representação visual das tabelas e das dependências, que é a linhagem.
  4. Operação (o "operational corner"):
    • o catálogo e o schema padrão, para as tabelas sem o namespace de três níveis;
    • o acesso às settings, que é assunto da próxima demo;
    • o agendamento, que na prática cria um Lakeflow Job com uma única task apontando para o pipeline;
    • o share para colegas;
    • o compute, com o serverless sugerido por padrão;
    • o botão azul de execução.

Uma dica: ajuste o layout ao que está fazendo, fechando os painéis de arquivos ao codar e ocultando o workspace ao ver os resultados.

O que guardar: o ETL tradicional em bronze, silver e gold funciona, mas relê e reprocessa tudo, reexecuta as views, deixa a qualidade fora do pipeline e não tem monitoramento do dado nem UI. O Structured Streaming resolve o reprocessamento, mas traz checkpoints, triggers e ciclo de vida para gerenciar. Os SDP respondem a isso com ingestão eficiente, transformação inteligente e operações automatizadas, dando processamento incremental, qualidade, infraestrutura gerenciada e visibilidade. Um pipeline se cria como ETL pipeline, e o editor reúne os arquivos, o código, a saída com o pipeline graph e a operação.
