Privileges in Unity Catalog

Get Started with Data Governance on Databricks · Lição 3

Em desenvolvimento

Esta lição, do Módulo 3 (Unity Catalog Permission Model), trata dos privilégios: o mecanismo, baseado no ANSI SQL DCL (Data Control Language), que controla quem pode fazer o quê em cada objeto securável da hierarquia. Cobre a propriedade (ownership), as concessões explícitas, as ACLs, os tipos de privilégio e a herança.

Estas anotações partem de um resumo da leitura da lição, não da lição inteira. Algumas partes não foram abertas, e isso está indicado no fim da página. A prática é a Demo 4, que concede a cadeia de privilégios ao secondary principal.

O modelo de segurança de dados

O modelo opera por ACLs, apoiado em ownership e em grants explícitos:

  • o dono do objeto tem implicitamente o ALL PRIVILEGES;
  • os demais principais (usuários ou grupos, como o analysts) precisam receber os privilégios explicitamente (por exemplo, o SELECT).

Isso facilita a governança descentralizada, porque os donos de domínio gerenciam o acesso aos seus próprios ativos. No exemplo, a tabela t pertence a um usuário (que tem todos os privilégios implícitos), o grupo analysts recebeu o SELECT e o dbadmins recebeu o ALL PRIVILEGES.

Controles de acesso centralizados

Há dois métodos, que ficam sincronizados:

  1. a sintaxe explícita do ANSI SQL DCL;
  2. a UI do Catalog Explorer.
GRANT <privilege> ON <securable_type> <securable_name> TO <principal>

-- exemplo da lição
GRANT SELECT ON iot.events TO engineers

O comando define o nível de permissão e o objeto securável (catálogo, schema, tabela, view, volume, modelo e outros), e concede a grupos sincronizados do provedor de identidade. O DCL centralizado é uma boa prática, porque aplica a segurança em todas as cargas de trabalho e em bancos federados.

ACLs

Uma ACL liga principais a privilégios sobre securáveis. A verificação ocorre sempre contra os metadados centrais do metastore, independentemente do compute usado. As listas do diagrama da lição, que não são exaustivas, são:

Tipos de privilégio

A lista é detalhada e granular, por tipo de ativo, e segue o princípio do menor privilégio: da criação ampla (CREATE CATALOG) ao acesso específico a dados (SELECT, READ FILES e EXECUTE). Essa granularidade é essencial para a segurança corporativa e a conformidade.

  • No metastore (lista não exaustiva): CREATE CATALOG, CREATE CONNECTION, CREATE EXTERNAL LOCATION, CREATE PROVIDER, CREATE RECIPIENT, CREATE SHARE, CREATE STORAGE CREDENTIAL, SET SHARE PERMISSION, USE MARKETPLACE ASSETS, USE PROVIDER, USE RECIPIENT e USE SHARE.
  • Em objetos: READ FILES, WRITE FILES, CREATE EXTERNAL LOCATION e CREATE EXTERNAL TABLE, USE SCHEMA, CREATE TABLE, CREATE VOLUME, CREATE FUNCTION, CREATE MODEL, CREATE MATERIALIZED VIEW e outros.

Os privilégios de compartilhamento (USE PROVIDER, USE RECIPIENT e USE SHARE) são os mesmos que a Demo 2 cita no open sharing.

Um stepper interativo da lição compara o modelo explícito (fino, mas com mais trabalho administrativo) com os modelos herdados do schema e do catálogo (escaláveis, com o escopo limitado à fronteira do contêiner).

Cenário: criar uma tabela

  • Criar uma tabela exige o CREATE TABLE no schema pai (além do USE CATALOG e do USE SCHEMA, acima na hierarquia).
  • Criar um catálogo exige o CREATE CATALOG no metastore.

Como na consulta, os privilégios podem ser concedidos explicitamente ou herdados do catálogo, e governam quem pode contribuir com novos ativos para um domínio.

ModeloOnde os privilégios são concedidos
ExplícitoUSE CATALOG no catálogo, e USE SCHEMA mais CREATE TABLE no schema
HerdadoOs três privilégios (USE CATALOG, USE SCHEMA e CREATE TABLE) concedidos no catálogo

Conclusão

  • Ownership e grants: o dono tem o ALL PRIVILEGES implícito, e os demais precisam de um grant explícito.
  • ACLs: ligam os principais aos privilégios sobre os securáveis.
  • DCL centralizado: o GRANT e o REVOKE em ANSI SQL, ou o Catalog Explorer, de forma consistente em todas as cargas e bancos federados.
  • Explícito × herdado: consultar exige USE CATALOG, USE SCHEMA e SELECT, e os privilégios podem ser herdados do schema ou do catálogo, o que reduz o overhead.

O que guardar: o dono de um objeto tem tudo implicitamente, e os outros precisam de um GRANT. Para consultar uma tabela, são necessários USE CATALOG, USE SCHEMA e SELECT. Para criar uma tabela, o CREATE TABLE no schema, e para criar um catálogo, o CREATE CATALOG no metastore. Os privilégios podem ser explícitos ou herdados do schema ou do catálogo, e a verificação é sempre feita contra o metastore, seja qual for o compute.
