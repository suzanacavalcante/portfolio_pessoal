Governed Tagging, Discovery, and Lineage in Unity Catalog

Get Started with Data Governance on Databricks · Demo 3

Em desenvolvimento

Esta demo, de cerca de 32 minutos, trata de três capacidades do Unity Catalog: as governed tags e as tag policies, a descoberta de ativos (e como as tags alimentam o controle de acesso baseado em atributos, o ABAC) e o lineage de tabela e de coluna. Juntas, elas apoiam o stewardship dos dados.

Estas anotações partem de um resumo cronometrado da demo, não da transcrição. O SQL que aparece é um esboço meu, do que o resumo descreve, e não foi executado. A sintaxe exata deve ser conferida na documentação.

Requisitos

  • Um workspace com Unity Catalog, e o Databricks Runtime 17.3 LTS ou superior (ou serverless v4 ou superior), com o serverless habilitado.
  • Os privilégios CREATE CATALOG e USE CATALOG, CREATE SCHEMA e USE SCHEMA, e CREATE TABLE.

O setup usa o compute serverless, o notebook de classroom (o helper DA) e um job Lakeflow que cria o mesmo ambiente de HR analytics da Demo 2 (o catálogo db_office_<usuário>, o schema HR, as tabelas employees e employee_benefits e as views, entre elas a hr_master). Se o ambiente da demo anterior existir, ele só é detectado e reaproveitado, em segundos. Do zero, leva de 3 a 4 minutos. O job aparece como setup_batch_jobs_demo_4.

Conceitos de tags

ConceitoO que é
Tag policies (nível de conta)Governam as chaves e os valores permitidos, o que evita o "tag sprawl", e controlam quais tags podem ser referenciadas nas políticas ABAC. Geridas por UI, API ou SQL
Controle de acesso à marcaçãoÉ separado do acesso aos dados. Para definir as políticas, o admin precisa de um privilégio como MANAGE ou CREATE. Para aplicar uma tag governada, basta a permissão atribuída (aos data stewards e donos de domínio). Os stewards classificam sem mudar o significado da tag
CompatibilidadeAs governed tags se constroem sobre o sistema de tags que já existia no Unity Catalog. O histórico é preservado, e, quando se define uma política para uma chave (por exemplo, PII), as tags existentes com essa chave se tornam governadas
ABACUma regra reutilizável, como "mascarar toda coluna com a tag PII", aplica a função de máscara automaticamente em todo o Lakehouse. Está em public preview

Os três usos das governed tags

Acesso

Gestão de acesso

Servem de base para as regras ABAC, como a máscara automática das colunas PII.

Custo

Atribuição de custo

Integram com as budget policies, para atribuir o custo a um centro de custo.

System

System tags

Certificação, deprecação, auto-classificação e as tags de workspace.

Data classification

Uma IA agêntica detecta e marca PII automaticamente (mais de 12 tipos, além dos classificadores regionais e de domínio). As tabelas e colunas novas são escaneadas em cerca de 24 horas, com re-scans incrementais. Os achados vão para uma UI de revisão e para a tabela system.data_classification.results. Depois de validar, aplicam-se as tags e derivam-se as políticas ABAC (por exemplo, mascarar as colunas classificadas como e-mail). Está em public preview na AWS, no Azure e no GCP.

Open sharing

O metastore governa os shares, os recipients e os providers. As políticas do Unity Catalog valem mesmo quando os dados saem do Databricks: uma requisição autorizada recebe um token de curta duração para o storage, e uma não autorizada é negada.

Aplicando tags

As células usam o objeto DA (da.username, da.catalog_name e da.office_catalog).

Governed tags

São atributos de nível de conta, com valores permitidos predefinidos, criados por admins de conta ou de workspace na UI, e não por usuários via SQL. As seis da demo:

TagValores de exemplo
PIISSN, email, address
classificationsalary_masked, confidential e outros
geo_accessregion_filter
environmentproduction, staging, development
data_qualitycertified, experimental, deprecated
cost_centerHR, finance e outros

Não dá para criá-las nem renomeá-las por SQL, e só valem os valores permitidos. Por exemplo, environment = prod falha.

Tags não governadas

São metadados de negócio: pares chave-valor livres, para quem tem o privilégio de aplicar tags, via SET TAG ON <objeto>. Servem para o dono, o propósito, a sensibilidade, o projeto e assim por diante. O setup já aplicou algumas no catálogo, no schema, nas tabelas e nas views. Na demo, inspecionam-se as existentes e adicionam-se data_steward e contains_pii (livres, em nível de tabela) à employees, e data_quality e report_type (não governadas) à view hr_master.

Atribuindo governed tags

Em catálogo, schema, tabela e view, usa-se a mesma sintaxe SET TAG ON, com os valores permitidos: o environment no catálogo, o cost_center no schema HR e o data_quality na view HR_master.

Em colunas a sintaxe é diferente: usa-se ALTER TABLE ... ALTER COLUMN ... SET TAGS, porque as colunas não são objetos securáveis de primeira classe. O SET TAG ON funciona só em catálogos, schemas, tabelas, views e volumes.

-- esboço meu, a partir da descrição do resumo
-- objeto securável (schema, tabela, view...): SET TAG ON
SET TAG ON SCHEMA db_office.hr cost_center = 'HR';

-- coluna: ALTER TABLE ... ALTER COLUMN ... SET TAGS
ALTER TABLE db_office.hr.employees
ALTER COLUMN email SET TAGS ('PII' = 'email');

Na demo, a PII vai para as colunas SSN e e-mail, a geo_access para a região e a classification para o salário. Depois, verificam-se todas as tags (da employees, das colunas e do schema inteiro).

Lineage

O lineage é capturado de forma automática, em runtime, no compute, sem fiação manual, em nível de tabela e de coluna. Ele reutiliza o modelo de permissões do Unity Catalog e cobre tabelas, dashboards, notebooks, workflows, feature tables, arquivos e pipelines Lakeflow Spark Declarative. Mesmo datasets derivados por APIs Spark carregam as relações. O serviço de lineage lê os logs do cluster ou do SQL warehouse, monta o metadado e mostra o grafo na UI. Pode ser exportado por API para catálogos externos (Alation, Collibra e Microsoft Purview).

Bring your own lineage

Registra ativos externos (um dashboard do Tableau ou um objeto do Salesforce) como metadado externo no Unity Catalog, ligados a tabelas, modelos ou caminhos (a montante, a jusante e em nível de coluna), pelo Catalog Explorer ou pela API REST. Precisa de CREATE EXTERNAL METADATA no metastore e de MODIFY no objeto. As ressalvas:

  • o lineage externo não vai para as system tables de lineage (recupera-se por API);
  • escala para cerca de 10 mil objetos externos e 100 mil relações por metastore;
  • está em public preview.

Descoberta

Busca na UI

Usa-se a barra de busca do workspace e o Catalog Explorer. As consultas de tag têm o prefixo tag:: tag:data_quality:certified encontra a hr_master, e tag:cost_center:HR encontra os ativos do centro de custo HR. A busca alcança tabelas, views, modelos, volumes, dashboards, Genie Spaces e notebooks, e só mostra o que o usuário tem o privilégio de ver.

  • A correspondência é exata na chave e no valor (por exemplo, PII:SSN).
  • As governed tags se comportam como as tags normais na busca e têm um ícone de cadeado.
  • A busca não encontra catálogos, schemas nem colunas por tag. Se não há resultados, a tag deve estar só em um catálogo ou schema, ou faltam privilégios.
  • Para uma exploração mais estruturada, usa-se o filtro de tag do Catalog Explorer.

Busca por SQL

As views do information_schema (table_tags e as de colunas) respondem a perguntas como:

  • as tabelas e views com sensitivity = high (a employees);
  • os ativos de HR certificados (a hr_master);
  • as colunas com a tag PII (e-mail e SSN da employees);
  • as colunas com qualquer tag governada (e-mail, região, salário e SSN, com a classification = confidential no salário e a geo_access = region_filter na região).

Na próxima demo, essas tags derivam as políticas ABAC de máscara e de filtro.

Lineage na prática

Com as tags, sabe-se que a employees tem PII, e o lineage identifica as views e os modelos que herdam dessas colunas. A consulta a information_schema.table_lineage ou a system.access.table_lineage pode retornar vazio, porque as system tables atualizam em até 24 horas. Isso é normal, e a UI não tem esse atraso.

  1. No Catalog Explorer, abre-se a HR_master e a aba Lineage (alternando entre upstream e downstream). A view é construída por um job Lakeflow, a partir da employees e da employee_benefits.
  2. O See lineage graph abre um grafo interativo (clicar em um nó o expande).
  3. O lineage de coluna (o ícone de lineage na coluna) destaca, por exemplo, o employee_ID.
  4. A lista mostra cerca de cinco ativos de tabela (duas tabelas e três views) mais dois ativos de job Lakeflow, com um filtro por tipo (notebooks, pipelines, consultas e dashboards).
  5. Expandir a employees revela a view manager_employee_summary.

Análise de impacto: a partir de uma tabela com PII, rastreiam-se todos os ativos que herdam dela. É o que o passo 5 mostra, com a manager_employee_summary.

Limpeza e conclusão

A limpeza fica comentada (o run_destroy_pipeline encontra ou cria o job destroy_batch_jobs_demo_4 e desfaz tudo, e os recursos ausentes são tratados como limpos). Ela foi mantida comentada porque a próxima demo reaproveita os objetos. Os pontos principais:

  • as governed tags e as tag policies classificam em nível de conta e controlam quem aplica qual tag;
  • a descoberta acontece pelo Catalog Explorer e pelo information_schema;
  • o lineage automático de tabelas e colunas habilita a análise de impacto;
  • as tags, os metadados e o lineage aparecem juntos (o significado de negócio ao lado da estrutura técnica), o que apoia o stewardship e as decisões de acesso conscientes de risco.

Ponto a conferir: o resumo menciona um ponto sobre a diferenciação de maiúsculas e minúsculas nas tags, mas diz que o trecho foi cortado na leitura. Não anotei essa regra, e vale conferir no vídeo.

O que guardar: as governed tags têm chaves e valores definidos por uma tag policy, criada no nível de conta, e quem as aplica não muda o significado delas. Em objetos usa-se o SET TAG ON, e em colunas o ALTER COLUMN ... SET TAGS. As tags alimentam a busca (tag:chave:valor, com correspondência exata) e as regras ABAC (por exemplo, mascarar tudo o que é PII). O lineage é capturado em runtime, em tabela e coluna, e permite a análise de impacto.
