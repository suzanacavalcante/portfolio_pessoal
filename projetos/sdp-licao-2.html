Simplified Pipeline Development and Common Pipeline Settings

Build Data Pipelines with Lakeflow Spark Declarative Pipelines · Lição 2

Em desenvolvimento

Esta lição trata de duas coisas: o editor multi-arquivo, que simplifica o desenvolvimento de pipelines, e as configurações mais comuns de um pipeline (compute, code assets e configuration). O objetivo é saber identificar e configurar essas opções e desenvolver um pipeline funcional com o novo editor e com SQL.

Estas anotações partem de um resumo da leitura da lição, não da lição inteira. Algumas partes não foram abertas, e isso está indicado no fim da página.

O editor multi-arquivo

Em vez de um único arquivo grande, o pipeline é organizado como um conjunto de arquivos, visíveis no navegador de assets. Edita-se o código e configuram-se os componentes em um só lugar. Segundo o anúncio (Data + AI Summit 2025), o código pode ser escrito em arquivos .sql ou .py (o recomendado) ou em notebooks. O editor traz recursos para:

  • construir pipelines robustos e agilizar o fluxo de desenvolvimento;
  • depurar com ferramentas integradas;
  • validar sem execuções completas (é o dry run da Demo 2).

As configurações do pipeline

No editor, o ícone de engrenagem abre o popup Pipeline settings, sem sair do ambiente. As três configurações mais comuns são:

1

Compute

Os recursos e o ambiente de execução.

2

Code Assets

Os arquivos e módulos de código do pipeline.

3

Configuration

Os parâmetros do pipeline.

Compute

Há as abas Serverless e Classic (Fixed Size). A serverless é a recomendada:

  • custo e desempenho otimizados, e foco no código, sem gerenciar infraestrutura;
  • refresh incremental de materialized views, e um otimizador baseado em custo, para transformações de MVs rápidas e eficientes;
  • Serverless Performance Optimized: uma opção para Lakeflow Jobs sensíveis ao tempo, para melhorar a responsividade.

Code Assets

Gerenciam os arquivos e módulos de código. Em Configure paths:

CampoO que faz
Pipeline Root FolderInclui automaticamente os arquivos relevantes da pasta do projeto, salvo especificação contrária. Pode ser uma pasta Git, para controle de versão e colaboração. Segundo o formulário, é anexada ao sys.path do Python, para importar módulos e pacotes dessa pasta
Source CodeDefine quais subpastas ou arquivos entram no pipeline (scripts Python, arquivos SQL, notebooks e outros). São processados quando o pipeline roda

Configuration

É um mapa de pares chave-valor para parametrizar o código. Os motivos para usar:

  1. melhora a legibilidade e a manutenção, ao centralizar os valores-chave;
  2. permite reutilizar os parâmetros em vários arquivos, sem hardcode;
  3. deixa o pipeline flexível e fácil de atualizar, sem mexer em vários pontos do código.

Um exemplo é o parâmetro source, que aponta para o caminho de um volume. No SQL se usa ${source}, substituído em tempo de execução:

CREATE STREAMING TABLE bronze
SELECT *
FROM STREAM read_files("${source}/orders", format => 'JSON');

Sobre o código acima: ele é o do resumo, copiado como está. Como exemplo, ele omite o AS e o OR REFRESH que usamos nas demos, então não o tomo como o formato exato da sintaxe.

O painel completo

O painel de settings reúne:

  1. Pipeline settings: o ID, o tipo (ETL pipeline), o nome, o criador e o Run as;
  2. Code assets: a root folder, o source code e o Configure paths;
  3. Default location for data assets: o catálogo e o schema padrão;
  4. Compute: serverless;
  5. Configuration: por exemplo, source com o caminho do volume;
  6. Tags: o Add tags.

Abaixo ainda há o Budget, a política de orçamento serverless. É o mesmo painel que vimos na Demo 2.

Conclusão

  1. Streaming tables, materialized views e views atendem a padrões de processamento diferentes, da ingestão incremental às agregações atualizadas e às consultas sob demanda.
  2. A sintaxe SQL declarativa dá um jeito consistente de criar datasets, e o Databricks gerencia as dependências pelo Declarative Pipeline Graph.
  3. O editor multi-arquivo reúne assets, edição modular, visualização do DAG, prévias de dados, informações de execução e ferramentas de validação.
  4. As configurações permitem personalizar o compute, os code assets, os parâmetros e as opções adicionais, para facilitar a gestão, o reuso e a escala.

O que não li: a explicação de cada número da imagem interativa da interface (só abri a do Pipeline Asset Browser, e a tabela acima das outras áreas é a minha descrição a partir do resumo), a aba Classic do compute, os links de documentação e as notas "Saiba mais". Nada disso está nestas anotações.

O que guardar: o editor multi-arquivo organiza o pipeline em arquivos (.sql ou .py) e valida sem rodar tudo. As três configurações comuns são o Compute (serverless é o recomendado, com refresh incremental de MVs), o Code Assets (a root folder e o source code) e a Configuration (pares chave-valor, usados com ${chave} no SQL para evitar hardcode).
