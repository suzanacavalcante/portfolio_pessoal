Deploying a Pipeline to Production

Build Data Pipelines with Lakeflow Spark Declarative Pipelines · Demo 4

Em desenvolvimento

Esta demo, de cerca de 20 minutos, estende o pipeline com o status dos pedidos, que passa pelas camadas bronze, silver e gold. Uma materialized view junta orders e status. Na parte operacional, revisa o modo do pipeline, as notificações e o event log, que pode ser configurado e consultado.

Estas anotações partem de um resumo cronometrado da demo, não da transcrição. O código é uma reconstrução minha a partir desse resumo e não foi executado.

Os dados e o join

Os orders já são conhecidos (customer_id, notifications, order_id, order_timestamp e _rescued_data). O order_id serve de chave para o join com o status, que está em outra pasta do volume source. Para um mesmo order_id há vários status ao longo do tempo. O caso ideal é: pedido feito, preparado, em espera e entregue.

A célula de teste usa duas CTEs (orders e status) e um INNER JOIN por order_id, trazendo order_id, order_timestamp e order_status.

O DAG alvo

Criação do pipeline por código

A função create_declarative_pipeline, do setup, configura o nome ("10-Deploying a Pipeline to Production"), a pasta raiz, o catálogo e o schema padrão e os code assets. Agora há duas pastas, orders e status. O pipeline abre na página de monitoramento e depois no editor.

O código de status

ObjetoO que faz
status_bronze (streaming table)Lê a pasta status do volume, com metadados. Ganha um comment, que reforça a busca no Unity Catalog, e table properties, aqui para explicitar a camada (normalmente se usam propriedades ou tags)
status_silver (streaming table)Duas expectations, valid_timestamp (com ON VIOLATION DROP ROW) e valid_order_status (só valores permitidos). Seleciona order_id, order_status e status_timestamp
full_order_info_gold (MV)O join de status e orders por order_id
canceled_orders_gold (MV)Filtra o status cancelado e traz uma coluna extra, com os dias até o cancelamento
delivered_orders_gold (MV)Filtra o status entregue
 
CREATE OR REFRESH STREAMING TABLE status_bronze
COMMENT 'Status brutos dos pedidos, vindos do volume'
TBLPROPERTIES (
    'layer' = 'bronze',
    'pipeline.reset_allowed' = 'false'
)
AS
SELECT *, current_timestamp() AS processing_time, _metadata.file_name AS source_file
FROM STREAM read_files('${source}/status', format => 'json');

CREATE OR REFRESH STREAMING TABLE status_silver (
    CONSTRAINT valid_timestamp EXPECT (status_timestamp > '2021-12-25') ON VIOLATION DROP ROW,
    CONSTRAINT valid_order_status EXPECT (order_status IN ('on the way', 'canceled', 'return canceled', 'delivered', 'return processed', 'placed', 'preparing'))
) AS
SELECT order_id, order_status, status_timestamp
FROM STREAM(status_bronze);

CREATE OR REFRESH MATERIALIZED VIEW full_order_info_gold AS
SELECT o.order_id, o.order_timestamp, s.order_status, s.status_timestamp
FROM status_silver s
INNER JOIN orders_silver o ON s.order_id = o.order_id;

O ponto que mais chama a atenção é a propriedade pipeline.reset_allowed = false. Ela protege a tabela de ser truncada em um full table refresh, o que evita perder os dados já processados.

Sobre o código acima: o resumo só nomeia os objetos e as regras. A lista de valores permitidos de status, o nome da propriedade layer, o alias status_timestamp e os textos dos comentários são meus. A condição do valid_timestamp aparece no resumo como "order_timestamp > 25/12/2021", mas usei status_timestamp, porque a silver de status não seleciona o order_timestamp. Vale conferir no vídeo.

Execução

O run usa o sdp_1_bronze como padrão, e o grafo mostra orders e status. São dois arquivos separados, e o serviço gerencia a ordem das dependências sozinho:

  1. os bronzes de orders e de status rodam em paralelo;
  2. depois, os silvers;
  3. a MV full_order_info_gold espera as duas silvers;
  4. por fim, as MVs de entregues e de canceladas.

Em seguida, uma célula do notebook adiciona mais JSONs, e uma nova execução mostra a ingestão incremental em todas as tabelas.

Consultando o event log

A consulta à tabela do event log (event_log_demo10) mostra as ações, as execuções e as modificações. Ele serve para auditoria, checagem de qualidade, progresso e linhagem. As colunas são: id, sequência, origem (informações do compute), timestamp, mensagem, nível, event_type e details (uma string JSON).

  • O event_type varia (update_progress, user_action, create_update, user_code_context, runtime_details, data_life_cycle e outros), e o conteúdo vai em details.
  • O flattening usa o operador : para extrair atributos do JSON (flow_progress, user_action). Nem todo tipo traz dados, então vale consultar a documentação.
  • Uma view temporária (dq_source_vw) converte o details com from_json, informando o schema, e usa o explode para listar as expectations (flow_progress → data_quality → expectations). Depois agrega, por dataset e expectation, os passing_records e os warning_records.
-- esboço meu: o schema do from_json é só ilustrativo
CREATE OR REPLACE TEMP VIEW dq_source_vw AS
SELECT
    explode(from_json(
        details:flow_progress.data_quality.expectations,
        'array<struct<name:string, dataset:string, passed_records:bigint, failed_records:bigint>>'
    )) AS row_expectations
FROM event_log_demo10
WHERE event_type = 'flow_progress';

O ganho é a observabilidade sem depender da UI. Dá para montar um Lakeflow Job com duas tasks: a primeira roda o pipeline SDP, e a segunda é um notebook que extrai esses insights e decide se a execução foi bem-sucedida.

Ponto a conferir: o resumo fala em passing_records e warning_records na agregação, mas não diz de onde vêm esses campos. No esboço acima usei nomes que conheço do JSON do event log (passed_records e failed_records), então os nomes exatos da demo podem ser outros.

O que guardar: o SDP resolve a ordem das dependências sozinho, e os fluxos independentes rodam em paralelo. A propriedade pipeline.reset_allowed = false protege uma tabela do full table refresh. Em produção: automatic recovery habilitada, Run as com service principal, notificações por e-mail (e Lakeflow Jobs para outros canais) e modo Triggered. O event log registra tudo em uma tabela, e o campo details é um JSON que se explora com o operador :, com from_json e com explode.
