Visão geral

Software está em transporte, saúde, energia e finanças. Onde há software importante, há quem procure uma falha para tirar vantagem. Desenvolver com segurança é construir sabendo que isso vai acontecer.

Esta página reúne o que estudei, da mentalidade (Security by Design) ao detalhe técnico (como se defender de injeção de SQL e XSS), passando pelo risco das bibliotecas de terceiros, pelas ferramentas que encontram falhas no código, pelo OWASP e pelos padrões de segurança para a nuvem.

Três palavras que não são sinônimos

Fraqueza

Vulnerabilidade

Uma falha no código, na configuração ou no desenho que pode ser explorada.

Tentativa

Ataque

A ação de alguém tentando explorar uma vulnerabilidade, tenha dado certo ou não.

Consequência

Intrusão

Quando o ataque funciona e há acesso não autorizado ao sistema ou aos dados.

Corrigir vulnerabilidades antes do ataque é muito mais barato do que lidar com a intrusão depois.

Mentalidade

Security by Design

Significa colocar a segurança como requisito desde o início, e não tentar "colar" uma camada de proteção no fim do projeto. A lógica é parecida com a do TDD: assim como testes acompanham o código desde a primeira linha, as análises e rotinas de segurança também acompanham.

Elementos principais

Avaliação de ameaças

Identificar logo no início o que pode atacar o sistema. Um formulário de login, por exemplo, já nasce como alvo de injeção.

Menor superfície de ataque

Expor apenas o necessário a quem não é autorizado. O que não está exposto não pode ser explorado.

Princípio do menor privilégio

Cada pessoa ou serviço acessa só o mínimo para cumprir sua função, o que limita o estrago de qualquer comprometimento.

Segmentação de rede

Isolar as partes do sistema. APIs e bancos de dados ficam em sub-redes privadas, sem acesso direto da internet.

Validação e sanitização

Toda entrada do usuário é validada antes de ser usada, para barrar injeções e estouros de memória.

Criptografia

Dados pessoais, principalmente os sensíveis, protegidos em repouso e em trânsito.

Testes de segurança contínuos

Varreduras de vulnerabilidade e revisões de código durante todo o desenvolvimento.

Educação em segurança

Todo o time, e não só quem atua em segurança, conhece as boas práticas.

Normas e regulamentações

Existem muitas normas, e variam por indústria, país e tipo de dado. Seguir todas é inviável e desnecessário. A recomendação é escolher uma base internacional (como a ISO 27001/27002) somada à que regula o setor em que se atua. Cumpri-las também funciona como garantia para os clientes.

Casos que ficaram conhecidos

SQL Injection · 2011

Sony PlayStation Network

Uma aplicação web não validava as entradas e permitiu a execução de comandos SQL maliciosos. Dados pessoais de milhões de contas foram expostos e a rede ficou fora do ar por dias, com grande dano à reputação.

XSS · 2005

MySpace

Um script injetado no próprio perfil se espalhava para todo mundo que o visitava e chegou a centenas de milhares de perfis em questão de horas. A rede teve de ser tirada do ar para conter o problema.

Os dois ataques são antigos, muito divulgados e totalmente evitáveis. Ainda assim, continuam acontecendo.

Injeção e XSS na prática

O ponto em comum desses ataques é misturar dado com comando. Quando a entrada do usuário é concatenada em uma consulta, em uma linha de comando ou em uma página HTML, ela pode ser interpretada como código. A defesa é sempre separar os dois e validar o que entra.

SQL Injection

Com a entrada ' OR '1'='1, a consulta concatenada passa a retornar todas as linhas. A correção é a consulta parametrizada: o banco recebe o comando e os valores separadamente, e o valor nunca é interpretado como SQL.

import sqlite3


def buscar_inseguro(conn, email):
    # VULNERÁVEL: a entrada vira parte do comando SQL
    consulta = f"SELECT id, nome FROM usuarios WHERE email = '{email}'"
    return conn.execute(consulta).fetchall()


def buscar_seguro(conn, email):
    # SEGURO: consulta parametrizada, o valor nunca é interpretado como SQL
    return conn.execute(
        "SELECT id, nome FROM usuarios WHERE email = ?", (email,)
    ).fetchall()


# Com a entrada "' OR '1'='1":
#   buscar_inseguro -> devolve todos os usuários
#   buscar_seguro   -> devolve lista vazia (nenhum e-mail igual a esse texto)
import java.sql.*;

class UsuarioDao {

    // VULNERÁVEL: a entrada vira parte do comando SQL
    ResultSet buscarInseguro(Connection conn, String email) throws SQLException {
        String sql = "SELECT id, nome FROM usuarios WHERE email = '" + email + "'";
        return conn.createStatement().executeQuery(sql);
    }

    // SEGURO: PreparedStatement separa o comando dos valores
    ResultSet buscarSeguro(Connection conn, String email) throws SQLException {
        PreparedStatement ps = conn.prepareStatement(
                "SELECT id, nome FROM usuarios WHERE email = ?");
        ps.setString(1, email);
        return ps.executeQuery();
    }
}

    (void)ctx; (void)n; (void)colunas;
    printf("%s %s\n", valores[0], valores[1]);

void buscar_inseguro(sqlite3 *db, const char *email) {
    char sql[256];
    snprintf(sql, sizeof sql,
             "SELECT id, nome FROM usuarios WHERE email = '%s'", email);
    sqlite3_exec(db, sql, imprimir_linha, NULL, NULL);
}

/* SEGURO: comando preparado e valor associado separadamente */
void buscar_seguro(sqlite3 *db, const char *email) {
    sqlite3_stmt *stmt;
    sqlite3_prepare_v2(db, "SELECT id, nome FROM usuarios WHERE email = ?",
                       -1, &stmt, NULL);
    sqlite3_bind_text(stmt, 1, email, -1, SQLITE_TRANSIENT);
    while (sqlite3_step(stmt) == SQLITE_ROW) {
        printf("%d %s\n", sqlite3_column_int(stmt, 0),
               (const char *)sqlite3_column_text(stmt, 1));
    }
    sqlite3_finalize(stmt);
}

Command Injection

O mesmo erro, agora com o sistema operacional: ao montar um comando de shell com texto do usuário, uma entrada como 8.8.8.8; cat /etc/passwd executa um segundo comando. A defesa é não usar shell, passar os argumentos como lista e validar o formato esperado.

import ipaddress
import subprocess


def ping_inseguro(host: str):
    # VULNERÁVEL: o texto inteiro é interpretado por um shell
    subprocess.run(f"ping -c 1 {host}", shell=True)


def ping_seguro(host: str):
    ipaddress.ip_address(host)       # Valida: lança ValueError se não for um IP
    # Sem shell: cada argumento é passado separadamente, nada é reinterpretado
    subprocess.run(["ping", "-c", "1", host], check=False)
import java.io.IOException;

class Rede {

    // VULNERÁVEL: o texto inteiro é interpretado por um shell
    void pingInseguro(String host) throws IOException {
        Runtime.getRuntime().exec(new String[]{"sh", "-c", "ping -c 1 " + host});
    }

    // SEGURO: valida o formato e executa sem shell, com argumentos separados
    void pingSeguro(String host) throws IOException, InterruptedException {
        if (!host.matches("\\d{1,3}(\\.\\d{1,3}){3}")) {
            throw new IllegalArgumentException("Host inválido");
        }
        new ProcessBuilder("ping", "-c", "1", host).inheritIO().start().waitFor();
    }
}

static bool so_digitos_e_pontos(const char *s) {
    if (*s == '\0') return false;
    for (; *s; s++) {
        if (!isdigit((unsigned char)*s) && *s != '.') return false;
    }
    return true;
}

/* SEGURO: valida o formato e executa sem shell (execlp) */
bool ping_seguro(const char *host) {
    if (!so_digitos_e_pontos(host)) return false;

    pid_t pid = fork();
    if (pid == 0) {
        execlp("ping", "ping", "-c", "1", host, (char *)NULL);
        _exit(127);
    }
    int status;
    waitpid(pid, &status, 0);
    return true;
}

Cross-Site Scripting (XSS)

Se um comentário com <script> é colocado na página sem tratamento, o navegador de quem a visita executa o script e pode enviar dados da sessão, como cookies, para o atacante. A defesa principal é o escape na saída: caracteres especiais do HTML viram texto inofensivo. Em geral, o escape automático dos motores de template já faz isso, e o perigo está em contorná-lo.

from html import escape


def renderizar_inseguro(comentario: str) -> str:
    # VULNERÁVEL: o texto do usuário vira HTML
    return f"<p>{comentario}</p>"


def renderizar_seguro(comentario: str) -> str:
    # SEGURO: < > & e aspas viram entidades HTML
    return f"<p>{escape(comentario)}</p>"


# Entrada: <script>roubar(document.cookie)</script>
#   inseguro -> o navegador executa o script
#   seguro   -> o texto aparece na tela, sem ser executado
// Biblioteca OWASP Java Encoder: org.owasp.encoder:encoder
import org.owasp.encoder.Encode;

class Comentarios {

    // VULNERÁVEL: o texto do usuário vira HTML
    String renderizarInseguro(String comentario) {
        return "<p>" + comentario + "</p>";
    }

    // SEGURO: escapa caracteres especiais para o contexto HTML
    String renderizarSeguro(String comentario) {
        return "<p>" + Encode.forHtml(comentario) + "</p>";
    }
}
package comentarios

// (o pacote html/template faz isso automaticamente)

#include <stdio.h>
#include <string.h>

/* VULNERÁVEL: o texto do usuário vai direto para o HTML */
void renderizar_inseguro(const char *comentario) {
    printf("<p>%s</p>", comentario);
}

/* SEGURO: escreve em 'saida' a versão escapada.
   Retorna 0 se coube no buffer e -1 se não coube. */
int escapar_html(const char *entrada, char *saida, size_t tamanho) {
    size_t n = 0;
    for (; *entrada; entrada++) {
        const char *troca = NULL;
        switch (*entrada) {
            case '&':  troca = "&amp;";  break;
            case '<':  troca = "&lt;";   break;
            case '>':  troca = "&gt;";   break;
            case '"':  troca = "&quot;"; break;
            case '\'': troca = "&#39;";  break;
        }
        size_t len = troca ? strlen(troca) : 1;
        if (n + len + 1 > tamanho) return -1;     /* evita estourar o buffer */
        if (troca) memcpy(saida + n, troca, len); else saida[n] = *entrada;
        n += len;
    }
    saida[n] = '\0';
    return 0;
}

Em C, o risco é maior: além da injeção, existe o estouro de buffer (buffer overflow), quando se escreve além da memória reservada. Repare no exemplo acima que a função recebe o tamanho do buffer e confere antes de cada escrita. Funções como strcpy e gets, que não fazem essa checagem, devem ser evitadas.

Regras gerais de defesa

  • Nunca confiar na entrada: validar tipo, tamanho e formato no servidor, preferindo listas do que é permitido a listas do que é proibido.
  • Separar dado de comando: consultas parametrizadas, argumentos em lista e escape na saída.
  • Menor privilégio: o usuário do banco da aplicação não precisa poder apagar tabelas.
  • Camadas extras: cabeçalhos como Content-Security-Policy e cookies HttpOnly reduzem o estrago de um XSS que passe.
Cadeia de suprimentos

Bibliotecas de terceiros: licenças e riscos

Importar uma biblioteca é adicionar ao projeto um componente que não foi escrito por você. Isso traz duas preocupações: a jurídica (a licença permite o seu uso?) e a de segurança (o código é confiável?).

Licenças mais comuns

LicençaPerfilO que exige
MITMuito permissivaManter o aviso de direitos autorais e o texto da licença
Apache 2.0Permissiva, com proteção de patentes e de contribuidoresManter avisos e indicar alterações
BSDPermissiva, parecida com a MITManter avisos; as variações mudam em detalhes
GPLCopyleft forteSoftware derivado também precisa ser distribuído sob a GPL

Os pontos de atenção são a compatibilidade entre as licenças das bibliotecas e a do seu projeto, a responsabilidade legal por usar código sem direito e o efeito na liberdade de uso do que você distribui. Uma dependência GPL em um produto proprietário, por exemplo, pode ser um problema sério.

O risco de segurança: o caso UA-Parser-JS

Em 2021, três versões do pacote npm UA-Parser-JS, que tinha cerca de 8 milhões de downloads por semana, foram publicadas com código malicioso que minerava criptomoeda (Monero) sem o conhecimento de quem usava. É o chamado cryptojacking: o processamento da máquina das vítimas é usado em silêncio em benefício do atacante. Uma biblioteca simples, usada só para interpretar um texto, virou porta de entrada.

Antes de importar

  • Usar fontes confiáveis, como repositórios oficiais
  • Olhar a popularidade e a comunidade ao redor
  • Ver quando houve a última manutenção
  • Considerar uma auditoria do código quando for crítico

Depois de importar

  • Monitorar vulnerabilidades conhecidas (ex.: npm audit)
  • Manter as dependências atualizadas
  • Rodar testes de segurança com regularidade
  • Usar análise estática de código

Análise estática de código

É o exame automatizado do código-fonte sem executá-lo, buscando bugs, vulnerabilidades, problemas de estilo e oportunidades de melhoria. Diferente dos testes dinâmicos, ela não precisa de um ambiente rodando, então pode acontecer cedo e a cada alteração. Também apoia a manutenibilidade: código legível, modular, testado e padronizado é código mais fácil de manter e de proteger.

Outros projetos da OWASP

Dependency-Track

Gestão de dependências: cruza as bibliotecas do projeto com bases públicas de vulnerabilidades (como a NVD do NIST) e classifica o risco. Funciona melhor integrada ao CI, com monitoramento regular e uma política de dependências aceitas.

Juice Shop

Uma loja virtual deliberadamente vulnerável, em Node.js, para praticar a exploração em um ambiente controlado, com desafios contínuos e realistas.

WebGoat

Plataforma de treinamento em lições isoladas, cada uma sobre um tipo de vulnerabilidade (injeção, XSS, autenticação, controle de acesso). Disponível em mais de uma tecnologia.

Web Security Testing Guide

Guia de testes de segurança de aplicações web: coleta de informações, configuração, identidade, autenticação, sessão, validação de entrada e tratamento de erros.

ZAP

Ferramenta de varredura que encontra vulnerabilidades em uma aplicação em execução, o que complementa a análise estática.

Juice Shop ou WebGoat? Os dois se complementam. O WebGoat ensina vulnerabilidade por vulnerabilidade, em lições guiadas. O Juice Shop dá uma aplicação inteira e deixa você procurar falhas por conta própria.

Infraestrutura

Padrões de segurança na nuvem

Código seguro precisa de uma infraestrutura segura. O Well-Architected Framework, adotado pelos grandes provedores de nuvem, organiza boas práticas em seis pilares, e a segurança é um deles.

Na AWS, três ferramentas ajudam a avaliar o ambiente: a Well-Architected Tool (revisão guiada da arquitetura), o Trusted Advisor (recomendações de melhoria) e o Security Hub, que verifica o ambiente contra padrões de segurança.

Padrões que o Security Hub verifica

PadrãoFoco
Melhores práticas básicas da AWSConjunto base de boas práticas de segurança do próprio provedor

As cinco funções do NIST Cybersecurity Framework

  • Identificar: conhecer ativos, riscos e governança.
  • Proteger: controles de acesso, treinamento, segurança de dados.
  • Detectar: monitoramento contínuo para perceber anomalias e eventos.
  • Responder: planejar a resposta, comunicar, analisar e mitigar.
  • Recuperar: planos de recuperação para retomar a operação.

ISO 27001 e ISO 27002

ISO 27001: o "o quê"

Requisitos para implantar e certificar um SGSI: escopo e contexto, política de segurança da informação documentada e avaliação e tratamento de riscos.

ISO 27002: o "como"

Guia de controles e boas práticas: políticas, gestão de ativos, segurança em recursos humanos e controle de acesso.

Os ganhos: gestão de riscos estruturada, apoio à conformidade legal, cultura de segurança, confiança de clientes e parceiros e um ciclo de melhoria contínua por auditorias e revisões.

O que levo daqui

  • Segurança começa no desenho e acompanha o ciclo inteiro. Consertar depois custa muito mais.
  • A raiz de injeção e XSS é a mesma: misturar dado com comando. A defesa é parametrizar, escapar e validar.
  • Toda dependência é código de terceiros rodando com as permissões do meu sistema, e precisa de critério antes de entrar.
  • Licença também é requisito: o que cabe juridicamente no projeto faz parte da qualidade.
  • Análise estática e varreduras no pipeline encontram problemas cedo e de forma repetível.
  • O OWASP Top 10 e os padrões de nuvem funcionam como mapa para saber onde olhar.
  • Segurança é um processo contínuo de identificar, proteger, detectar, responder e recuperar, e não um estado final.
