Centralized Governance with UC with External Compute Engines

Data Interoperability with Unity Catalog · Lição 7

Em desenvolvimento

Esta lição, do Módulo 3 (casos de uso de interoperabilidade), apresenta o segundo grande caso de uso: as cargas de transformação e escrita rodam em engines externos (EMR e Flink), enquanto o Unity Catalog continua impondo a governança sobre os dados que eles leem e escrevem.

Estas anotações partem de um resumo da leitura da lição. Segundo o resumo, a lição foi lida por completo (a página não tinha blocos expansíveis), e o diagrama da seção de contexto apareceu como texto Mermaid sem renderizar. A prática é a Demo 3, com o AWS EMR.

O contexto

Aqui a Databricks deixa de ser o hub de computação. Os engines externos fazem o trabalho pesado, e o Unity Catalog permanece como o único ponto de governança sobre as tabelas.

A diferença-chave em relação ao caso de uso 1: as transformações e atualizações são feitas pelo compute externo, e não pela plataforma Databricks. O Unity Catalog atua puramente como camada de governança e de metadados.

As metas:

  • estabelecer o Unity Catalog como a camada central de governança e de metadados;
  • permitir que os engines externos executem transformações diretamente em tabelas Iceberg gerenciadas do Unity Catalog;
  • manter a governança unificada, aproveitando a computação especializada.

A implementação de referência: escrevendo dados do Unity Catalog a partir do EMR

Ela espelha o padrão do processamento centralizado, mas acrescenta os privilégios de escrita, já que o engine externo vai modificar as tabelas do Unity Catalog. O pré-requisito é um usuário ou service principal com o papel Account Admin habilitado, e um papel equivalente no sistema externo.

LadoPassos
Databricks
  1. Habilitar o External Data Access no nível do metastore (Iceberg REST).
  2. Criar as tabelas gerenciadas: Iceberg gerenciada ou Delta com UniForm.
  3. Criar uma service principal, com um client secret.
  4. Conceder os privilégios: EXTERNAL USE SCHEMA, SELECT, MODIFY e USE no catálogo e no schema, para a service principal.
EMR
  1. Provisionar o cluster EMR, com o Spark e as bibliotecas de runtime do Iceberg.
  2. Configurar o Spark para o Unity Catalog: a URI do catálogo REST, a URI do token e o client ID e o secret da service principal, na configuração do Spark.
  3. Rodar o ETL contra as tabelas do Unity Catalog: referenciar as tabelas como destino dos jobs Spark e gravar de volta pelo REST catalog.

O privilégio MODIFY: diferentemente do padrão somente leitura, este cenário exige o MODIFY no schema, porque o engine externo faz operações de escrita.

Outros sistemas: o mesmo padrão vale para o Spark standalone em Kubernetes, o Dataproc, o Trino e o Flink. Cada um tem a sua sintaxe de configuração do Iceberg REST catalog e das credenciais.

Ligação com a Demo 3: é exatamente o que a Demo 3 faz: uma service principal dedicada (EMR Integration) com o MODIFY e o SELECT, o Spark no EMR escrevendo na store_sales_iceberg e a auditoria por principal. A ligação é minha.

Key Takeaways

  • O Unity Catalog oferece governança centralizada mesmo quando o compute é externo.
  • Os engines externos precisam do privilégio MODIFY para escrever (ao contrário do acesso somente leitura).
  • O Iceberg REST Catalog e o credential vending permitem um compute externo seguro.
  • Todas as operações são auditadas e governadas pelo Unity Catalog, independentemente do engine.

O que guardar: neste caso, o trabalho pesado roda no engine externo (EMR, Flink ou Spark), e o Unity Catalog só governa. A receita é a da leitura, mais o MODIFY: o external data access no metastore, as tabelas Iceberg ou Delta com UniForm, uma service principal com os grants e, no engine, a configuração do catálogo REST, com as credenciais da service principal. Tudo é auditado no Unity Catalog, seja qual for o engine.
