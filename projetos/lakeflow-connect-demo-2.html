Data Ingestion with CREATE TABLE AS and COPY INTO

Data Ingestion with Lakeflow Connect · Demo 2

Em desenvolvimento

Esta demo, de cerca de 11 minutos, ingere dados de duas formas: o CTAS (CREATE TABLE AS) com a função read_files, e o COPY INTO, para ingestão incremental. No caminho, ela compara tabelas gerenciadas e externas e mostra como o COPY INTO lida com mudanças de schema.

Estas anotações partem de um resumo da demo com marcação de tempo, não da transcrição. Os comandos abaixo são exemplos escritos por mim a partir desse resumo, com nomes genéricos no lugar dos caminhos e das tabelas do curso, e não foram executados.

Setup e dados de origem

O ambiente é o da demo anterior: compute serverless e o script de configuração, que define o catálogo labuser e o schema data_ingestion como padrão. Confirma-se o catálogo e o schema atuais.

A origem é o caminho dbacademy_ecommerce → raw → user_historical, com quatro arquivos Parquet e alguns de metadados. As colunas são user_id, user_first_touch_timestamp e email.

Dá para consultar o arquivo direto, com SELECT * FROM formato.`caminho_absoluto`, mas isso só lê os dados e não os ingere.

SELECT * FROM parquet.`caminho_do_volume/user_historical`;

A função read_files

A read_files dá mais controle do que a consulta direta. As principais opções, vistas na documentação:

OpçãoPara quê
formatO tipo do arquivo, como Parquet, text ou XML
schemaDefinir o schema explicitamente. O Unity Catalog também detecta o schema automaticamente
inferColumnTypesSe os tipos das colunas devem ser inferidos
partitionColumnsAs colunas de partição
schemaHintsDeclarar agora colunas que podem chegar no futuro. Enquanto não há dados, o valor vem como null, e quando os dados chegam, entram na tabela

Método 1: CTAS

A read_files(caminho, format => ...) devolve os dados mais a coluna _rescued_data, incluída por padrão para capturar o que não casa com o schema inferido.

Como o catálogo e o schema padrão já estão definidos, basta o nome da tabela. Para reexecutar, faz-se antes um DROP TABLE IF EXISTS.

DROP TABLE IF EXISTS usuarios_ctas;

CREATE TABLE usuarios_ctas AS
SELECT * FROM read_files(
    'caminho_do_volume/user_historical',
    format => 'parquet'
);

DESCRIBE EXTENDED usuarios_ctas;

O DESCRIBE EXTENDED mostra as quatro colunas (as três da origem mais a _rescued_data), as estatísticas do Delta e os detalhes da tabela: tipo, otimização preditiva, proprietário, provedor e localização.

O equivalente em Python

O spark.read.format(...).load(caminho) carrega os dados em um DataFrame, e o .write grava a tabela no modo overwrite, que sobrescreve se a tabela já existir. O resultado é o mesmo do SQL.

df = spark.read.format("parquet").load("caminho_do_volume/user_historical")

df.write.mode("overwrite").saveAsTable("usuarios_python")

Método 2: COPY INTO

O COPY INTO carrega dados incrementalmente da origem para uma tabela do Unity Catalog. Ele é repetível e idempotente: rodar de novo o mesmo comando não copia os mesmos dados outra vez.

Exemplo 1: incompatibilidade de schema

A tabela de destino não tem a coluna email, que existe na origem. O COPY INTO devolve um erro de schema incompatível. A correção é o COPY_OPTIONS ('mergeSchema' = 'true'): o schema é mesclado, uma nova coluna é criada e as linhas são inseridas. O resultado mostra as linhas afetadas, inseridas e ignoradas.

-- destino sem a coluna email (os tipos aqui são só ilustrativos)
CREATE TABLE IF NOT EXISTS usuarios_copy (
    user_id STRING,
    user_first_touch_timestamp BIGINT
);

COPY INTO usuarios_copy
FROM 'caminho_do_volume/user_historical'
FILEFORMAT = PARQUET
COPY_OPTIONS ('mergeSchema' = 'true');

Exemplo 2: evolução de schema preventiva

Aqui não se informa schema nenhum, apenas o formato e o mergeSchema = true, em uma tabela com outro nome.

CREATE TABLE IF NOT EXISTS usuarios_copy_2;

COPY INTO usuarios_copy_2
FROM 'caminho_do_volume/user_historical'
FILEFORMAT = PARQUET
COPY_OPTIONS ('mergeSchema' = 'true');

Idempotência

Rodar o COPY INTO de novo na tabela que já existe devolve que nenhum arquivo foi afetado ou inserido, porque os arquivos já tinham sido carregados.

Os dois métodos lado a lado

CTAS com read_filesCOPY INTO
O que fazCria a tabela a partir do resultado de uma consultaCarrega dados de forma incremental em uma tabela
ReexecuçãoPrecisa de um DROP TABLE IF EXISTS antesÉ idempotente: não copia os mesmos dados de novo
Mudança de schemaVem do que foi inferido, com a coluna _rescued_dataErro de schema incompatível, resolvido com mergeSchema

O que guardar: uma consulta direta ao arquivo só lê, e a read_files permite controlar o formato, o schema e as dicas de colunas. O CTAS cria a tabela com os dados mais a coluna _rescued_data, e o equivalente em Python usa read e write com overwrite. Tabelas gerenciadas são o padrão e apagam os dados no DROP TABLE, e as externas guardam só os metadados. O COPY INTO é incremental e idempotente, e o mergeSchema resolve a diferença de schema entre a origem e o destino.
