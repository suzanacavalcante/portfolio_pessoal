Change Data Capture with AUTO CDC with SCD Type 1

Build Data Pipelines with Lakeflow Spark Declarative Pipelines · Demo 5

Em desenvolvimento

Esta demo, de cerca de 18 minutos, completa o pipeline com os customers. Os JSONs entram no bronze, passam por uma segunda tabela bronze com expectations e chegam a uma silver que é a "ground truth" dos clientes. O que leva os dados até ela é o AUTO CDC INTO com SCD Type 1, que sobrescreve os dados.

Estas anotações partem de um resumo cronometrado da demo, não da transcrição. O código é uma reconstrução minha a partir desse resumo e não foi executado.

Preparação e dados

O ponto de partida é um notebook em serverless v5, com o classroom setup (o mesmo catálogo, os schemas bronze, silver e gold e o volume source), agora com a pasta customers. As colunas dos JSONs são address, city, customer_id, email, name, operation, state, timestamp, zip_code e _rescued_data.

A coluna operation (às vezes chamada de status, então vale confirmar o nome com o time) diz o que fazer com cada registro: INSERT, UPDATE ou DELETE. Ela é essencial em CDC.

O pipeline "12 – Change Data Capture with AUTO CDC" é criado pela create_declarative_pipeline, que é uma função do classroom setup e não do framework (o código está na pasta includes). As fontes são as pastas customers, orders e status.

O código de customers

Bronze

customers_bronze_raw

Streaming table com comment e table properties (a alternativa são as tags). Usa pipelines.reset_allowed para impedir o truncamento em um full refresh, e lê a pasta customers com read_files e STREAM, com metadados.

Bronze

customers_bronze_clean

Lê do raw (é permitido ter várias tabelas por camada) e prepara os dados antes do CDC, com cinco expectations. O código é só um SELECT * com o timestamp de leitura.

Silver

scd_type1_customer_silver

Streaming table sem schema declarado, porque o AUTO CDC cuida disso. Só tem um comment.

As expectations do customers_bronze_clean

ExpectationRegraAção e motivo
valid_idcustomer_id não nuloFAIL UPDATE. Sem o ID não dá para decidir entre inserir e atualizar, então falha tudo
valid_operationoperation não nulaDROP ROW. Sem a operação não se sabe o que fazer

CREATE OR REFRESH STREAMING TABLE customers_bronze_clean (
    CONSTRAINT valid_id EXPECT (customer_id IS NOT NULL) ON VIOLATION FAIL UPDATE,
    CONSTRAINT valid_operation EXPECT (operation IS NOT NULL) ON VIOLATION DROP ROW,
    CONSTRAINT valid_name EXPECT (name IS NOT NULL OR operation = 'DELETE'),
    CONSTRAINT valid_address EXPECT (address IS NOT NULL OR operation = 'DELETE'),
    CONSTRAINT valid_email EXPECT (
        rlike(email, '^([a-zA-Z0-9_\\-\\.]+)@([a-zA-Z0-9_\\-\\.]+)\\.([a-zA-Z]{2,5})$')
        OR operation = 'DELETE'
    ) ON VIOLATION DROP ROW
)
AS
SELECT *, current_timestamp() AS processing_time
FROM STREAM(customers_bronze_raw);

Dica do instrutor: o padrão de quarantine é uma tabela secundária que captura os registros descartados, para não perder dados. Ele foi citado, mas não demonstrado.

AUTO CDC INTO

Um flow é o "elo" entre uma origem e um destino. Neste pipeline há três: volume para bronze, bronze para clean, e clean para silver. A sintaxe do AUTO CDC INTO é parecida com a do MERGE INTO. A diferença é que o MERGE INTO tem estilo batch (compara toda a origem com o destino a cada execução) e não é ideal para streaming, enquanto o AUTO CDC é feito para streaming. Conhecer o MERGE ajuda a entender o AUTO CDC.

CREATE OR REFRESH STREAMING TABLE scd_type1_customer_silver
COMMENT 'Clientes, com a versão mais recente de cada um';

CREATE FLOW customers_flow AS
AUTO CDC INTO scd_type1_customer_silver
FROM STREAM customers_bronze_clean
KEYS (customer_id)
APPLY AS DELETE WHEN operation = 'DELETE'
SEQUENCE BY timestamp
COLUMNS * EXCEPT (timestamp, _rescued_data, operation)
STORED AS SCD TYPE 1;
ElementoO que faz
Tabela alvo e origemO alvo é a silver, e a origem é FROM STREAM customers_bronze_clean
KEYSA chave de comparação (customer_id). Pode haver várias. Se a chave existe, atualiza. Se não existe, insere
APPLY AS DELETE WHENOpcional. Define quando o registro é um delete. Sem isso, só há update
SEQUENCE BYA coluna que ordena as múltiplas mudanças, para ficar com a mais recente. É o aspecto de tempo do streaming
COLUMNS * EXCEPTTira timestamp, _rescued_data e operation. A silver é a "ground truth" e só tem colunas de negócio
STORED AS SCD TYPE 1Sobrescreve os dados. O Type 2 mantém o histórico

Sobre o código acima: o resumo descreve os elementos, mas não traz o texto do código. O nome do flow, o regex do e-mail, os comentários e o SEQUENCE BY timestamp (uso a coluna timestamp porque ela é a que o EXCEPT remove) são meus. A forma exata de declarar o flow (com ou sem o CREATE FLOW) pode ser diferente na demo.

Primeira execução

O grafo mostra orders, status e customers. A scd_type1_customer_silver mostra 939 upserted records e 0 deletados, e a consulta confirma 939 registros. Antes da segunda carga, os dois clientes acompanhados são a Sandy Adams (com endereço em "Jacqueline Mountains") e o Stephen Green.

Segunda carga

Um segundo JSON (01.json) é adicionado nas pastas orders, status e customers. O de customers tem cerca de 23 registros, com deletes e inserts. A Sandy Adams ganha um novo endereço, e o Stephen Green será deletado.

ExecuçãoResultado
1ª (baseline)939 upserts, 0 deletes, 939 registros na silver
2ª (novo arquivo)Ingestão incremental. 23 registros passam do bronze ao customers_bronze_clean (cinco expectations) e vão ao AUTO CDC: 22 upserts e 1 delete (Stephen Green). A silver fica com 948 registros

Na consulta final, a Sandy Adams aparece com o endereço atualizado (sobrescrito, que é a característica do Type 1), e o Stephen Green não aparece mais.

Ponto a conferir: o resumo diz que o arquivo tem "muitos DELETEs", mas conta só 1 delete (22 upserts e 1 delete somam os 23). Pelas contas, 948 = 939 − 1 + inserts, então seriam cerca de 10 inserts entre os 22 upserts, e o resto seriam updates. É uma dedução minha. Vale conferir no vídeo.

O que guardar: o CDC aplica à tabela destino as mudanças (INSERT, UPDATE e DELETE) de uma origem. No SDP isso é o AUTO CDC INTO, o equivalente em streaming do MERGE INTO. Ele precisa de KEYS, de um SEQUENCE BY para ordenar e do STORED AS SCD TYPE 1 (sobrescreve) ou Type 2 (guarda o histórico). Antes do CDC, convém limpar a origem com expectations, como a valid_id com FAIL UPDATE, e descartar o que não dá para processar.
