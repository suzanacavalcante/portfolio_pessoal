Change Data Capture (CDC) Overview

Build Data Pipelines with Lakeflow Spark Declarative Pipelines · Lição 5

Em desenvolvimento

Esta lição apresenta o Change Data Capture (CDC) e os dois tipos principais de Slowly Changing Dimensions, o SCD Type 1 (sobrescreve) e o SCD Type 2 (guarda o histórico). Também apresenta o AUTO CDC INTO e o fluxo Customers que completa o pipeline. A prática é a Demo 5.

Estas anotações partem de um resumo da leitura da lição, não da lição inteira. Algumas partes não foram abertas, e isso está indicado no fim da página.

O que é Change Data Capture

É uma técnica para rastrear e capturar as mudanças de uma fonte de dados (banco, lakehouse ou data warehouse) e aplicá-las a uma tabela de destino, como o Lakehouse, mantendo-a com o estado mais recente da origem. A origem traz INSERTs, UPDATEs e DELETEs, e a tabela de mudanças precisa ser uma streaming table.

O CDC é categorizado em tipos de Slowly Changing Dimensions (SCD), que dizem como o histórico das mudanças é tratado. Os principais são o Type 1 e o Type 2.

SCD Type 1: sobrescrever

EventoO que acontece
UpdateO registro anterior é sobrescrito, pela chave, com o novo valor
DeleteO registro deletado pela chave é removido
InsertNão há rastreamento de chaves ou linhas antigas. Só o dado atual é mantido

Exemplo passo a passo

A tabela alvo customers tem dois clientes. A tabela de origem updates traz as mudanças, e a chave é o CustomerID, com o ProcessDate como coluna de sequência.

A tabela alvo fica com as últimas informações de cada cliente, sem versões históricas.

SCD Type 2: histórico

  • Update e insert: o registro antigo é preservado, com uma coluna adicional que indica o seu período de validade (data de início, de fim ou uma flag de atual). Uma nova linha entra com a informação atualizada.
  • Delete: o registro marcado como deletado é mantido, e uma coluna indica que ele está inativo.
  • Quando usar: quando o histórico importa e é preciso rastrear como os atributos mudam ao longo do tempo (por exemplo, o endereço ou o status de um cliente).

O Type 2 acrescenta duas colunas de metadados à tabela alvo: __START_AT (quando a linha ficou ativa) e __END_AT (quando ficou inativa, se for o caso). Um __END_AT nulo quer dizer que a linha está ativa agora.

Comparando com o Type 1: no mesmo exemplo, o Type 1 termina com 2 linhas (Peter e Kostas), e o Type 2 com 4. A diferença é que o Type 2 guarda o endereço antigo do Peter e o registro do Samarth, que o Type 1 apaga.

AUTO CDC INTO

Esta parte do resumo só aponta para a documentação: as AUTO CDC APIs simplificam o change data capture no SDP. Antes elas se chamavam APPLY CHANGES, com a mesma sintaxe. A explicação de cada cláusula (KEYS, APPLY AS DELETE WHEN, SEQUENCE BY, COLUMNS e STORED AS) está na Demo 5.

O fluxo Customers no pipeline

  1. Ingerir os JSONs de clientes do cloud storage para a streaming table customers_bronze.
  2. Criar a customers_bronze_clean, uma streaming table limpa, que filtra e formata os updates, inserts e deletes incrementais do bronze.
  3. Usar o AUTO CDC INTO para a silver de clientes, com o STORED AS SCD TYPE 1, que sobrescreve as mudanças (updates, inserts e deletes).

O fluxo final combina a lógica de CDC com a arquitetura medalhão, para manter os clientes atualizados, sem histórico. Isso é importante para as análises a jusante, para o compliance e para a personalização.

Conclusão

  1. O CDC rastreia e captura inserts, updates e deletes do sistema de origem e os aplica a uma tabela alvo, mantendo o Lakehouse em sincronia.
  2. O SCD Type 1 sobrescreve o destino com os valores mais recentes e não retém histórico. É a abordagem mais simples e eficiente quando só os dados atuais importam.
  3. O SCD Type 2 preserva cada versão histórica, com __START_AT e __END_AT. As linhas ativas têm o __END_AT nulo, e as inativas e deletadas carregam uma data. Isso permite a análise histórica completa.
  4. O AUTO CDC INTO é o mecanismo declarativo embutido do Lakeflow. Ele substitui a lógica complexa de batch do MERGE INTO por uma sintaxe concisa e legível, em que cada cláusula tem um papel distinto.
  5. O fluxo Customers completa a arquitetura e produz uma silver de clientes atual e pronta para produção.

O que não li: o início da lista de objetivos e da introdução (que ficaram acima do trecho que li), as notas "Saiba mais" e os links de documentação. A tabela comparativa e o parágrafo "Comparando com o Type 1" são meus, montados a partir dos exemplos do resumo.

O que guardar: o CDC aplica à tabela destino os inserts, updates e deletes de uma origem. O Type 1 sobrescreve e apaga, e mantém só o estado atual. O Type 2 mantém o histórico, com __START_AT e __END_AT (nulo quer dizer ativa). O AUTO CDC INTO, que antes se chamava APPLY CHANGES, faz isso de forma declarativa, no lugar do MERGE INTO em batch.
