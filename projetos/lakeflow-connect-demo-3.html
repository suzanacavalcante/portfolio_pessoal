Ingesting JSON Files with Databricks

Data Ingestion with Lakeflow Connect · Demo 3

Em desenvolvimento

Esta demo, de cerca de 17 minutos, ingere JSON bruto no Unity Catalog com CTAS e compara três formas de trabalhar com colunas JSON: a string achatada (flatten), o tipo STRUCT e o tipo VARIANT. O ponto de partida são eventos de um tópico Kafka, que chegam codificados.

Estas anotações partem de um resumo da demo com marcação de tempo, não da transcrição. Os comandos abaixo são exemplos escritos por mim a partir desse resumo, com caminhos genéricos, e não foram executados. Os valores do JSON de exemplo são inventados por mim, só para mostrar a forma.

Setup e dados de origem

O ambiente é o das demos anteriores: compute serverless e o script de configuração, com o catálogo labuser e o schema data_ingestion como padrão. A origem são os dados events-kafka do catálogo dbacademy_ecommerce (do Marketplace), com 11 arquivos.

Do dado bruto ao dado decodificado

Lido como texto, o dado mostra o formato cru de um tópico Kafka: key e value, ambos codificados em base64, além de offset, partition, timestamp e topic. Quando lidos como JSON, os dados são interpretados, mas continuam codificados.

  1. Salva-se o dado bruto em uma tabela bronze, a kafka_events_bronze_raw, sem nenhuma transformação.
  2. Decodifica-se: o unbase64(...) converte para binário, e o CAST(... AS STRING) produz a string JSON legível. O resultado vai para a kafka_events_bronze_decoded.
CREATE TABLE kafka_events_bronze_raw AS
SELECT * FROM read_files('caminho_do_volume/events-kafka', format => 'json');

CREATE TABLE kafka_events_bronze_decoded AS
SELECT
    offset,
    CAST(unbase64(key) AS STRING)   AS key,
    CAST(unbase64(value) AS STRING) AS value
FROM kafka_events_bronze_raw;

O offset é um inteiro, mas o value inteiro fica como uma única string. A partir daí, há três caminhos.

O JSON da amostra tem device (string), geo (objeto com city e state), items (um array de objetos), traffic_source, user_first_touch_timestamp e user_id.

Opção 1: achatar colunas de string JSON

Prós

Simples e flexível

É fácil de implementar e muito flexível: sem schema, o JSON vira texto simples.

Contras

Pouco eficiente

É difícil processar dados complexos, e sem schema pode haver problemas de integridade. Consultar exige código adicional.

Os campos simples (device e traffic_source) são extraídos com get_json_object. Já o geo e o items continuam como strings JSON, e para ler dentro deles é preciso decodificar de novo.

SELECT
    get_json_object(value, '$.device')         AS device,
    get_json_object(value, '$.traffic_source') AS traffic_source,
    get_json_object(value, '$.geo')            AS geo,    -- ainda é uma string JSON
    get_json_object(value, '$.items')          AS items   -- ainda é uma string JSON
FROM kafka_events_bronze_decoded;

Opção 2: tipo STRUCT

Prós

Schema e desempenho

O schema definido garante a integridade dos dados, e o desempenho é melhor.

Contras

Schema fixo

O schema é fixado desde o início. Se a estrutura do JSON mudar, como a ordem, fica complicado lidar, e a flexibilidade é menor.

Define-se o schema do JSON e aplica-se à coluna de string com o from_json. O schema pode ser escrito à mão ou obtido com o schema_of_json, a partir de um valor de exemplo. Na tabela kafka_events_bronze_struct, a coluna value passa a ser uma estrutura, e não mais uma string.

CREATE TABLE kafka_events_bronze_struct AS
SELECT
    offset,
    from_json(
        value,
        schema_of_json('{"device":"iOS","geo":{"city":"Nova York","state":"NY"},"items":[{"item_id":"X1"}],"traffic_source":"email","user_first_touch_timestamp":1,"user_id":"U1"}')
    ) AS value
FROM kafka_events_bronze_decoded;

Com a estrutura, as consultas são diretas: value.device, os campos aninhados como value.geo.city (no exemplo do curso, Nova York) e o size(value.items), que conta os elementos do array de STRUCT.

SELECT
    value.device,
    value.geo.city,
    size(value.items) AS qtd_itens
FROM kafka_events_bronze_struct;

explode e explode_outer

O explode transforma cada item do array em uma linha, um item por linha, repetindo a chave. Por padrão, arrays nulos ou vazios não geram linha. O explode_outer gera uma linha com null nesses casos. O resultado da demo foi salvo na tabela bronze_exploded_array.

CREATE TABLE bronze_exploded_array AS
SELECT offset, explode(value.items) AS item
FROM kafka_events_bronze_struct;

-- explode_outer mantém a linha com null quando o array é nulo ou vazio

Opção 3: tipo VARIANT

O VARIANT é um formato novo, aberto, flexível e de bom desempenho para strings JSON. Exige o Databricks Runtime 15.4 ou superior e, no serverless, uma versão maior que 1.

O parse_json(string_json) devolve um valor VARIANT, e a tabela kafka_events_bronze_variant é criada a partir da tabela decodificada. O acesso é fácil: o : acessa os campos, e o ::tipo converte para um tipo, como o ::string. Sem o cast, o resultado continua sendo VARIANT.

CREATE TABLE kafka_events_bronze_variant AS
SELECT offset, parse_json(value) AS value
FROM kafka_events_bronze_decoded;

SELECT
    value:device,                  -- continua VARIANT
    value:device::string AS device -- convertido para string
FROM kafka_events_bronze_variant;

Comparação das três opções

MétodoSchemaFlexibilidadeDesempenho e consultaQuando usar
String achatadaNenhumAltaBaixo, difícil de consultarIngestão simples, sem processar
STRUCTDefinido na ingestãoBaixa (estrutura fixa)BomJSON com estrutura estável
VARIANTFlexívelAltaBomJSON semiestruturado que muda

O que guardar: os dados do Kafka chegam em base64, e o caminho é gravar o dado bruto em uma tabela bronze e decodificar com unbase64 e CAST. A string achatada é simples, mas difícil de consultar. O STRUCT dá schema e desempenho, e o explode abre os arrays, mas a estrutura fica fixa. O VARIANT, com parse_json, o : e o ::tipo, une flexibilidade e bom desempenho. A demo recomenda ler a documentação sobre o VARIANT para saber mais.
