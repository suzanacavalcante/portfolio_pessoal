Interoperability Patterns Overview

Data Interoperability with Unity Catalog · Lição 3

Em desenvolvimento

Esta lição (a 1.3 do Módulo 1) apresenta os três padrões principais de interoperabilidade do Unity Catalog: o Iceberg REST Catalog, a catalog federation e a lakehouse federation. Em todos eles, o Unity Catalog é a camada central de governança. A lição também mapeia cada padrão à seção do curso em que ele é detalhado.

Estas anotações partem de um resumo da leitura da lição. Segundo o resumo, a lição foi lida por completo, e os cartões da matriz de escolha já exibiam as respostas. As demos do treinamento são a prática de cada padrão, e a tabela mais abaixo as relaciona.

O Unity Catalog como camada central de governança

O Unity Catalog fica acima da camada de armazenamento e aplica um único conjunto de controles de governança, independentemente do formato da tabela ou do engine que consulta. Ele cobre as tabelas gerenciadas, as tabelas Iceberg, as tabelas externas, as foreign tables, os volumes e os modelos. Seja qual for o padrão, o ativo é governado no Unity Catalog com:

  • o controle de acesso (inclusive o de granularidade fina);
  • a auditoria;
  • o lineage automatizado;
  • a descoberta.

Padrão 1: Iceberg REST Catalog

O Unity Catalog implementa a especificação aberta Apache Iceberg REST Catalog. Assim, engines externos compatíveis com o Iceberg podem ler (e, em alguns casos, escrever) as tabelas gerenciadas do Unity Catalog diretamente, sem copiar dados.

Quando usar:

  • engines analíticos downstream (Snowflake, Trino, Dremio e Starburst) precisam acessar as tabelas do Unity Catalog;
  • clientes Spark, Flink ou PyIceberg externos processam, fora da Databricks, dados governados pelo Unity Catalog;
  • quer-se uma única cópia no cloud storage, lida por vários engines.

Padrão 2: Catalog Federation

Registra um metastore externo (Hive Metastore ou AWS Glue) como foreign catalog no Unity Catalog, para que as suas tabelas sejam consultáveis por ele, sem mudar onde os dados vivem. Há ainda uma migração opcional, in-place, para tabelas gerenciadas.

Quando usar:

  • migrar de um metastore legado para o Unity Catalog sem interromper as cargas existentes;
  • dar a governança do Unity Catalog às tabelas gerenciadas por outro catálogo;
  • fazer uma adoção em fases, em que as tabelas foreign viram uma ponte para as tabelas gerenciadas.

Padrão 3: Lakehouse Federation

Registra uma connection com um banco operacional ou analítico externo (por exemplo, o PostgreSQL via Lakebase, o SQL Server ou o Snowflake) e cria um foreign catalog para consultar essa fonte no lugar, a partir do Unity Catalog. Isso permite consultas federadas e joins entre sistemas.

Quando usar:

  • juntar dados operacionais de um OLTP com dados analíticos do lakehouse, sem ETL;
  • expor dados de outro warehouse pela governança do Unity Catalog, com a movimentação mínima;
  • fazer o pushdown de filtros, projeções, agregações e joins para a fonte, onde houver suporte.

Cuidado com o nome: a catalog federation e a lakehouse federation às vezes são chamadas, as duas, de "Lakehouse Federation". A diferença está em o que é federado: um metastore (Hive Metastore ou Glue) ou um banco (SQL Server, PostgreSQL ou Snowflake).

Relacionado: Open Sharing

É um protocolo aberto separado, para compartilhar dados vivos com destinatários externos sem copiá-los, entre organizações e clouds. Está fora do escopo deste curso: a lição só o menciona por completude, porque ele foca no compartilhamento entre organizações, e não na consulta entre engines. (O treinamento anterior o citou na Demo 2, com os privilégios de open sharing.)

Key Takeaways

  • O Unity Catalog é a camada central de governança em qualquer padrão.
  • O Iceberg REST Catalog conecta engines Iceberg externos às tabelas gerenciadas do Unity Catalog.
  • A catalog federation liga os metastores legados (Hive Metastore e Glue) ao Unity Catalog.
  • A lakehouse federation expõe bancos externos (PostgreSQL/Lakebase, SQL Server e Snowflake) pelo Unity Catalog.
  • O Open Sharing serve ao compartilhamento entre organizações (fora de escopo aqui).

O que guardar: a pergunta que escolhe o padrão é "o que eu quero fazer?". Se é servir as tabelas do Unity Catalog a outro engine, é o Iceberg REST. Se é trazer um metastore externo (Hive ou Glue), é a catalog federation. Se é consultar um banco externo no lugar, é a lakehouse federation. Nos três, a governança é a do Unity Catalog. O Open Sharing é um caso à parte, para outra organização.
