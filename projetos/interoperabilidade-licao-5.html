Dois padrões de acesso aberto

O Unity Catalog expõe dois padrões de acesso aberto, que abrem as tabelas gerenciadas a vários engines externos sem abrir mão da governança. Os dois são especificações abertas.

O Spark aparece nos dois grupos. A regra da lição é usar a Unity REST API para as tabelas gerenciadas Delta e o IRC para as tabelas Iceberg. O credential vending, com credenciais curtas e restritas a um caminho, é o mecanismo por baixo das duas.

O Iceberg REST Catalog

O IRC padroniza como os engines descobrem e leem as tabelas Iceberg, e o Unity Catalog implementa a spec diretamente. Ele é um serviço de diretório centralizado, que dá metadados e acesso às tabelas Iceberg por uma API padrão. No exemplo da lição, o Spark cria a tabela, o Unity Catalog implementa a spec, e então o Trino a enxerga, o Flink a processa e o Snowflake a consulta.

Os benefícios são uma API padronizada para qualquer engine, uma interoperabilidade real sem duplicar dados e a implementação completa da spec pelo Unity Catalog.

Credential vending: o mecanismo por baixo

O credential vending não é um terceiro padrão de acesso. É o mecanismo que tanto a Unity REST API quanto o IRC usam para emitir credenciais curtas e restritas a clientes externos, sob demanda, mantendo a governança mesmo com a computação fora da Databricks.

  • A spec Iceberg REST carrega as credenciais emitidas direto na resposta do loadTable (nos campos config e storage-credentials). Assim, toda chamada REST Iceberg já é uma chamada de credential vending.
  • É o mesmo mecanismo usado quando um cluster Databricks lê uma tabela gerenciada. O acesso externo só expõe a maquinaria existente a engines que não são da Databricks.
  • O Delta Sharing é um protocolo irmão, governado pelo Unity Catalog, mas com desenho próprio: o servidor pré-assina as URLs dos arquivos de dados, sem emitir credenciais de storage ao cliente. Por isso, ele não usa o credential vending.

O fluxo

  1. O cliente externo se autentica no Unity Catalog.
  2. É autorizado no nível da tabela.
  3. A decisão de acesso é registrada, para a auditoria.
  4. Ele recebe uma credencial curta, restrita ao caminho, para ler ou escrever direto no cloud storage.
AspectoDetalhe
MecanismoGera credenciais temporárias e restritas para o acesso externo
GovernançaMantém a governança do Unity Catalog ao permitir o acesso externo
Controles de segurançaEscopos de acesso finos, expiração e rotação de tokens, e restrições por IP
AuditoriaAudit logging completo de todo acesso externo

Boa prática de segurança: use sempre o credential vending, com tokens de vida curta, no lugar de credenciais de longa duração. Configure restrições por IP e audite todos os padrões de acesso externo.

Configurando o acesso externo: quatro passos

PassoO que éDetalhes
1. Habilitar Abrir as portas no nível de workspace e de metastore Um toggle expõe o endpoint Iceberg REST do Unity Catalog, junto com as políticas de rede e de IP. As allow-lists são aplicadas antes de qualquer tráfego externo. Feito uma vez, por um responsável de plataforma ou governança, no console admin do workspace e nas configurações do metastore
2. Autenticar Identificar e confiar no chamador externo Uma service principal OAuth (ou um token por usuário, para dev e teste) é a identidade dos engines externos, com os grants do Unity Catalog e a allow-list de IP. O Unity Catalog emite tokens de acesso curtos e faz o vending das credenciais de storage só para os arquivos necessários. Configurado no Unity Catalog (a service principal e os grants) e no secret scope do workspace, que guarda o segredo
3. Conectar Ligar o engine externo ao Unity Catalog O engine recebe a URL do endpoint Iceberg REST, as credenciais da service principal, o nome do warehouse ou catálogo e as opções específicas. Depois disso, ele descobre, carrega e (com o MODIFY concedido) escreve nas tabelas, como em um catálogo Iceberg nativo. O mecanismo varia: o Snowflake usa uma CATALOG INTEGRATION, o EMR usa a configuração de catálogo do Spark e o PyIceberg usa load_catalog("rest", ...)
4. Monitorar Verificar, auditar e rotacionar as credenciais As operações do dia 2: a revisão de audit logs, as consultas a system tables, a rotação de segredos e a verificação de pushdown. A system.access.audit mostra quem acessou o quê, e a system.query.history mostra as consultas executadas pelo engine externo. Os segredos devem ser rotacionados periodicamente, e os grants ajustados conforme a necessidade

Os passos nas demos: a Demo 2 percorre os passos 1 a 3 com o Snowflake (o external data access no metastore, a service principal com os grants e a catalog integration), e a Demo 3 faz o mesmo com o EMR, acrescentando o MODIFY. O passo 4 (a auditoria por service principal) aparece na Demo 3. A ligação é minha.

Key Takeaways

  • A UC REST API dá acesso programático aos metadados, à governança e ao lineage.
  • O Iceberg REST Catalog permite que qualquer engine compatível com o Iceberg descubra e leia ou escreva as tabelas do Unity Catalog, pela spec aberta.
  • O credential vending é o mecanismo por trás dos dois: credenciais curtas e restritas a um caminho a cada acesso, o mesmo usado internamente na computação Databricks.
  • O Delta Sharing é um protocolo irmão, governado pelo Unity Catalog, mas com URLs pré-assinadas, distinto do credential vending.
  • O acesso externo mantém toda a governança do Unity Catalog (permissões, auditoria e lineage).
  • O setup segue 4 passos: Habilitar, Autenticar, Conectar e Monitorar.

O que guardar: há duas portas de entrada, a Unity REST API (para clientes Delta) e o Iceberg REST Catalog (para engines Iceberg), e as duas usam o credential vending: credenciais curtas, restritas ao caminho, emitidas a cada acesso e auditadas. O IRC lê as tabelas Iceberg e as Delta com UniForm (esta só leitura), e escreve nas Iceberg gerenciadas. Para configurar: habilitar o acesso externo, criar uma service principal OAuth, configurar o engine e monitorar e rotacionar.
