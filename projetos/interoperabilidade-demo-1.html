Interoperability and Performance Benefits of Managed Tables

Data Interoperability with Unity Catalog · Demo 1

Em desenvolvimento

Esta demo, de cerca de 9 minutos, tem duas partes: o efeito do liquid clustering no desempenho de uma tabela com bilhões de linhas, e a criação de uma tabela Iceberg gerenciada e de uma tabela Delta com UniForm, para verificar que clientes Iceberg externos conseguem acessá-las.

Estas anotações partem de um resumo da demo, não da transcrição. Segundo o resumo, a única legenda do vídeo está em chinês simplificado, e o resumo foi feito a partir dela, então algum detalhe pode ter se perdido na tradução. O SQL que aparece é um esboço meu e não foi executado.

O cenário

A demo usa o dataset TPC-DS com scale factor 1000. A tabela store_sales tem cerca de 2,8 bilhões de linhas.

Parte 1: liquid clustering e desempenho

O liquid clustering melhora as consultas porque permite ao planejador pular arquivos. O notebook de setup do instrutor já criou duas tabelas com os mesmos dados (cerca de 2,8 bilhões de linhas):

  • store_sales_unclustered, sem clustering;
  • store_sales_clustered, com liquid clustering pelas colunas de date key e item key.

A mesma consulta seletiva (uma janela de 7 dias e uma faixa de 11 itens) é rodada nas duas, comparando os arquivos lidos e os bytes lidos.

Sem clusteringCom liquid clustering
Tempo da consultacerca de 1 minuto3,45 s
Arquivos lidos1.0241
Dados escaneadosmais de 13,75 GBcerca de 7 MB
 
-- esboço meu: os nomes das colunas são os do TPC-DS e são só uma suposição
CREATE TABLE store_sales_clustered
CLUSTER BY (ss_sold_date_sk, ss_item_sk)
AS SELECT * FROM store_sales;

No vídeo, o DDL da tabela clusterizada aparece só como referência, e a consulta é literalmente a mesma nas duas tabelas.

O layout físico e a poda de arquivos

O DESCRIBE DETAIL mostra o layout físico (o número de arquivos, o tamanho e as colunas de clustering). Via Python, o tamanho em bytes é parecido nas duas tabelas, mas a clusterizada tem mais arquivos, porque o liquid clustering controla o layout, e mostra as colunas date key e item key.

Depois, mede-se quantos arquivos o Spark realmente abre, usando a coluna oculta _metadata.file_path, para calcular o percentual de poda:

TabelaArquivos podadosPoda
Sem clustering676 arquivos66%
Com liquid clusteringsó 1 arquivo foi lido99,96%

É isso que explica a diferença de cerca de 4 segundos contra cerca de 60.

Ponto a conferir: o resumo diz que a tabela sem clustering leu 1.024 arquivos e que a poda dela foi de 676 arquivos (66%). Pelas contas, 676 de 1.024 dá 66%, então o número de 1.024 parece ser o total que ela poderia ter lido, e não o que a consulta leu depois da poda. Não tenho como confirmar qual das duas leituras é a do vídeo.

Parte 2: interoperabilidade

Os mesmos dados store_sales e as mesmas chaves de clustering, agora para interoperar com sistemas externos:

Iceberg

Tabela Iceberg gerenciada

Criada com liquid clustering. Aqui, desabilita-se o deletion vectors e o row tracking, porque o leitor Iceberg do Snowflake não é compatível com esses recursos.

UniForm

Tabela Delta com UniForm

Com a propriedade delta.universalFormat.enabledFormats = iceberg, que permite aos clientes Iceberg lerem a tabela Delta. Nas propriedades, a compatibilidade Iceberg (v3) aparece como habilitada.

-- esboço meu: só a propriedade do UniForm vem do resumo
CREATE TABLE store_sales_uniform
CLUSTER BY (ss_sold_date_sk, ss_item_sk)
TBLPROPERTIES ('delta.universalFormat.enabledFormats' = 'iceberg')
AS SELECT * FROM store_sales;

Verificação com PyIceberg

Cria-se também uma tabela Delta comum (store_sales_delta_plain, sem UniForm) como referência. Instala-se o pyiceberg e conecta-se ao endpoint Iceberg REST do Unity Catalog, com a URL do workspace, um token de API e o catálogo e o schema da sessão. Carrega-se o metadado de três tabelas:

TabelaEsperadoResultado
Iceberg gerenciadaSucessoConectou

Isso demonstra a conectividade a partir de clientes Iceberg externos. As demos seguintes conectam o Snowflake e o AWS EMR a essas tabelas.

Conclusão

O liquid clustering dá ganhos enormes de poda de arquivos e de tempo. E tanto a tabela Iceberg gerenciada quanto a Delta com UniForm ficam acessíveis a clientes Iceberg externos pelo catálogo REST do Unity Catalog, enquanto uma Delta comum não fica.

Ligação com o treinamento anterior: as tabelas gerenciadas e as external locations vistas na lição Unity Catalog Fundamentals são a base para entender por que o catálogo consegue expor as tabelas por um endpoint aberto. A ligação é minha.

O que guardar: o liquid clustering faz o planejador pular arquivos (neste caso, de 1.024 arquivos e cerca de 13 GB para 1 arquivo e cerca de 7 MB, e de cerca de 60 s para 3,45 s). Para os clientes Iceberg externos acessarem os dados, há duas opções: uma tabela Iceberg gerenciada (sem deletion vectors nem row tracking, para o Snowflake) ou uma tabela Delta com o UniForm. Uma tabela Delta comum não aparece no endpoint Iceberg REST do Unity Catalog.
