Visão geral

Qualidade de software não é uma etapa no fim do projeto: é um conjunto de hábitos que acompanha o código desde a primeira linha. Testar é a forma mais direta de provar que o que foi escrito faz o que promete.

Esta página reúne o que estudei sobre como construir essa confiança em camadas: começando pelo TDD e pelos testes unitários, passando por ferramentas que inspecionam o código sem executá-lo e por dublês que isolam dependências, até testes de integração, de comportamento e de ponta a ponta.

1

Testar primeiro

TDD: o teste descreve o comportamento antes do código existir.

2

Inspecionar

Lint, estilo de código, cobertura e quality gates.

3

Isolar

Stubs, fakes, spies e mocks para controlar dependências.

4

Integrar

Testar controladores e APIs com requisições reais.

5

Validar o comportamento

BDD com Gherkin e testes de ponta a ponta.

Testes unitários

TDD: Desenvolvimento Orientado a Testes

Aprendemos a programar por tentativa e erro: escrevemos, rodamos, ajustamos. O TDD organiza essa intuição em um método. É um raciocínio hipotético-dedutivo: formulo uma hipótese sobre o comportamento ("se a conexão com o banco falhar, serei avisado do erro") e escrevo um teste que a confirma ou derruba. Só depois escrevo o código que faz o teste passar.

Começar falhando

Um truque do método: transformar a lista de comportamentos esperados em testes que falham de propósito. Um teste vazio é considerado sucesso pelo framework, então ele precisa nascer vermelho. A lista vira um checklist e cada teste que fica verde é uma pergunta respondida. É normal descobrir novos testes no meio do caminho.

Exemplo de ciclo completo

Uma função que aplica desconto em um preço, com os três testes que a descrevem: um caso comum, o limite e o caso inválido. Escolha a linguagem na aba abaixo.

def aplicar_desconto(preco: float, percentual: float) -> float:
    if not 0 <= percentual <= 100:
        raise ValueError("Percentual deve estar entre 0 e 100")
    return round(preco * (1 - percentual / 100), 2)

public class Desconto {
    public static double aplicar(double preco, double percentual) {
        if (percentual < 0 || percentual > 100) {
            throw new IllegalArgumentException("Percentual deve estar entre 0 e 100");
        }
        return Math.round(preco * (1 - percentual / 100) * 100.0) / 100.0;
    }
}

/* Em C não há framework embutido: assert.h já serve para um teste simples.
   Compilar com: gcc desconto.c -o desconto -lm && ./desconto */
#include <assert.h>
#include <math.h>
#include <stdbool.h>

/* Retorna false quando o percentual é inválido */
bool aplicar_desconto(double preco, double percentual, double *resultado) {
    if (percentual < 0 || percentual > 100) {
        return false;
    }
    *resultado = round(preco * (1 - percentual / 100) * 100) / 100;
    return true;
}

int main(void) {
    double r;

    /* deve aplicar desconto de 10 por cento */
    assert(aplicar_desconto(200, 10, &r) && r == 180.0);

    /* deve manter o preço quando o desconto é zero */
    assert(aplicar_desconto(200, 0, &r) && r == 200.0);

    /* deve falhar quando o percentual passa de 100 */
    assert(!aplicar_desconto(200, 120, &r));

    return 0;
}

Não é só Java: quase toda linguagem tem sua forma de escrever testes. Algumas das mais usadas: JUnit e TestNG (Java), xUnit e NUnit (C#), Jest e Mocha (JavaScript), pytest e unittest (Python), go test (Go), RSpec (Ruby), PHPUnit (PHP). O raciocínio é o mesmo em todas.

Anatomia de um teste

Todo teste unitário segue o mesmo padrão em três tempos, o Triplo A: Arrange (preparar o cenário), Act (executar a ação) e Assert (verificar o resultado). Os verificadores (asserts) variam: igualdade, nulo, verdadeiro, mesma referência, lançamento de exceção, além das versões negadas.

Ganchos de ciclo de vida

Frameworks como o JUnit permitem rodar código de preparação e limpeza em momentos fixos, o que evita repetir o mesmo setup em cada teste. Uma classe auxiliar pode concentrar o que é comum, como abrir conexão, gerar dados ou chamar uma API.

Gancho (JUnit 5)Quando executaUso típico
@BeforeAllUma vez, antes de todos os testes da classeSubir conexão ou configurar URL base
@BeforeEachAntes de cada testeCriar os objetos do cenário do zero
@TestO teste em siPreparar, agir e verificar
@AfterEachDepois de cada testeLimpar estado e fechar recursos
@AfterAllUma vez, depois de todos os testesEncerrar o que foi aberto no início

Em herança, a regra de ordem é: os ganchos "antes" da classe-base rodam primeiro e os "depois" dela rodam por último, de forma que a classe-base envolve a classe filha.

Boa prática: nome de teste descreve comportamento, não implementação. deveLancarErroQuandoPercentualPassaDe100 diz o que esperar, e quando falhar já indica onde procurar.

Inspeção

Análise estática e cobertura

Parte dos problemas pode ser encontrada sem executar o código. Os analisadores estáticos, chamados de lint, rodam na IDE, no terminal ou na integração contínua e avisam em tempo real sobre más práticas, bugs prováveis, vulnerabilidades e desvios de formatação. Cada alerta vem com uma explicação do porquê e uma sugestão de correção.

Qualidade

Lint (análise de problemas)

Procura code smells, bugs e falhas de segurança. Exemplos de alertas: variável privada nunca usada, captura de exceção genérica em vez de uma específica.

SonarLint, PMD, PyLint, ESLint, RuboCop.

Estilo

Code style (convenções)

Garante padrão de escrita e formatação, como camelCase para métodos e documentação obrigatória. Mantém todo o time escrevendo da mesma forma.

Checkstyle, StyleCop, Prettier, Black, Reek.

Cobertura de código

É a métrica que mostra quanto do código foi executado pelos testes. Ajuda a descobrir um if ou uma exceção que nenhum teste exercita. Ela indica o que não foi testado, mas não garante que o que foi testado está bem verificado: cobertura alta com asserts fracos é falsa segurança.

Quality gate

Ferramentas como o SonarQube reúnem métricas (code smells, falhas, vulnerabilidades, duplicação, cobertura) e viram um portão de qualidade na integração contínua. Se um Pull Request para a branch principal piora alguma dessas métricas, ele é barrado com o motivo. Dá para praticar integrando um projeto do GitHub ao SonarCloud.

Isolamento

Dublês de teste e Mockito

Um teste unitário deve falhar por causa do código que está sendo testado, não porque o banco de dados caiu. Quando o código depende de algo externo (banco, API REST, outra biblioteca), usamos dublês: objetos falsos que se comportam de forma controlada e previsível. Isso permite simular cenários felizes, erros previstos e até reproduzir um defeito visto em produção.

DublêO que fazExemplo
StubDevolve uma resposta fixa e pré-definidaUm cálculo que sempre retorna 10
FakeImplementação simplificada, mas funcionalBanco de dados em memória
SpyObserva e registra como foi chamadoContar quantas vezes um método rodou
MockDefine o comportamento esperado e verifica as interações"Quando receber X, retorne Y"

A estratégia que guardei: testes unitários usam mocks nas dependências externas, e testes integrados usam um fake, como um banco em memória, para ser rápido sem depender de infraestrutura. Tudo isso só funciona porque a classe recebe suas dependências por injeção de dependência, por meio de uma interface, e não as cria por conta própria. É a mesma ideia de portas e adaptadores vista em Arquiteturas de Software.

No Java, a biblioteca de referência é o Mockito. Em outras linguagens existem equivalentes (Moq em C#, Sinon.JS em JavaScript, RSpec em Ruby) e algumas já trazem isso embutido, como o unittest.mock do Python. Abaixo, um exemplo em que uma cobrança depende de um gateway de pagamento externo:

from unittest.mock import Mock
import pytest


class Cobranca:
    def __init__(self, gateway):          # Dependência injetada
        self.gateway = gateway

    def cobrar(self, valor):
        if valor <= 0:
            raise ValueError("Valor deve ser positivo")
        return "aprovada" if self.gateway.cobrar(valor) else "recusada"


def test_deve_aprovar_quando_gateway_autoriza():
    gateway = Mock()
    gateway.cobrar.return_value = True            # Define o comportamento (stub)

    assert Cobranca(gateway).cobrar(100) == "aprovada"
    gateway.cobrar.assert_called_once_with(100)   # Verifica a interação (mock)


def test_nao_deve_chamar_gateway_com_valor_invalido():
    gateway = Mock()

    with pytest.raises(ValueError):
        Cobranca(gateway).cobrar(0)

    gateway.cobrar.assert_not_called()

import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.ArgumentMatchers.anyLong;
import static org.mockito.Mockito.*;

interface Gateway {
    boolean cobrar(long centavos);
}

class Cobranca {
    private final Gateway gateway;                 // Dependência injetada

    Cobranca(Gateway gateway) {
        this.gateway = gateway;
    }

    String cobrar(long centavos) {
        if (centavos <= 0) {
            throw new IllegalArgumentException("Valor deve ser positivo");
        }
        return gateway.cobrar(centavos) ? "aprovada" : "recusada";
    }
}

@ExtendWith(MockitoExtension.class)
class CobrancaTest {

    @Mock
    Gateway gateway;

    @Test
    void deveAprovarQuandoGatewayAutoriza() {
        when(gateway.cobrar(10_000)).thenReturn(true);       // Define o comportamento

        assertEquals("aprovada", new Cobranca(gateway).cobrar(10_000));
        verify(gateway, times(1)).cobrar(10_000);            // Verifica a interação
    }

    @Test
    void naoDeveChamarGatewayComValorInvalido() {
        assertThrows(IllegalArgumentException.class,
                () -> new Cobranca(gateway).cobrar(0));

        verify(gateway, never()).cobrar(anyLong());
    }
}
package cobranca

import (
	"errors"
	"testing"
)

type Gateway interface {
	Cobrar(centavos int64) bool
}

type Cobranca struct {
	gateway Gateway // Dependência injetada
}

func (c Cobranca) Cobrar(centavos int64) (string, error) {
	if centavos <= 0 {
		return "", errors.New("valor deve ser positivo")
	}
	if c.gateway.Cobrar(centavos) {
		return "aprovada", nil
	}
	return "recusada", nil
}

// Dublê escrito à mão: age como stub (autoriza) e como spy (conta chamadas)
type gatewaySpy struct {
	autoriza bool
	chamadas int
}

func (g *gatewaySpy) Cobrar(int64) bool {
	g.chamadas++
	return g.autoriza
}

func TestDeveAprovarQuandoGatewayAutoriza(t *testing.T) {
	gw := &gatewaySpy{autoriza: true}

	got, _ := Cobranca{gw}.Cobrar(10000)

	if got != "aprovada" || gw.chamadas != 1 {
		t.Errorf("esperava aprovada com 1 chamada, recebi %q com %d", got, gw.chamadas)
	}
}

func TestNaoDeveChamarGatewayComValorInvalido(t *testing.T) {
	gw := &gatewaySpy{}

	_, err := Cobranca{gw}.Cobrar(0)

	if err == nil || gw.chamadas != 0 {
		t.Errorf("esperava erro sem chamar o gateway (chamadas: %d)", gw.chamadas)
	}
}

;; O gateway é só uma função recebida como argumento (injeção de dependência)
(defn cobrar [gateway valor]
  (when-not (pos? valor)
    (throw (IllegalArgumentException. "Valor deve ser positivo")))
  (if (gateway valor) "aprovada" "recusada"))

(deftest aprova-quando-gateway-autoriza
  (let [chamadas (atom [])
        gateway  (fn [valor] (swap! chamadas conj valor) true)]   ; stub + spy
    (is (= "aprovada" (cobrar gateway 10000)))
    (is (= [10000] @chamadas))))

(deftest nao-chama-gateway-com-valor-invalido
  (let [chamadas (atom 0)
        gateway  (fn [_] (swap! chamadas inc) true)]
    (is (thrown? IllegalArgumentException (cobrar gateway 0)))
    (is (zero? @chamadas))))
#include <assert.h>
#include <stdbool.h>
#include <stddef.h>
#include <string.h>

/* A dependência é um ponteiro para função, que podemos trocar por um dublê */
typedef bool (*Gateway)(long centavos, void *contexto);

/* Retorna NULL quando o valor é inválido */
const char *cobrar(Gateway gateway, void *contexto, long centavos) {
    if (centavos <= 0) {
        return NULL;
    }
    return gateway(centavos, contexto) ? "aprovada" : "recusada";
}

/* Dublê: age como stub (autoriza) e como spy (conta chamadas) */
typedef struct {
    bool autoriza;
    int chamadas;
} GatewayFalso;

static bool gateway_falso(long centavos, void *contexto) {
    (void)centavos;
    GatewayFalso *g = contexto;
    g->chamadas++;
    return g->autoriza;
}

int main(void) {
    /* deve aprovar quando o gateway autoriza */
    GatewayFalso a = {true, 0};
    assert(strcmp(cobrar(gateway_falso, &a, 10000), "aprovada") == 0);
    assert(a.chamadas == 1);

    /* não deve chamar o gateway com valor inválido */
    GatewayFalso b = {true, 0};
    assert(cobrar(gateway_falso, &b, 0) == NULL);
    assert(b.chamadas == 0);

    return 0;
}

O que olhar em um teste com mock

  • Definir o comportamento: "ao receber este parâmetro, devolva aquele valor". Se o código chamar com outro valor, o teste falha, porque o comportamento só foi definido para o primeiro. Em casos genéricos usam-se coringas, como anyString() e anyInt().
  • Verificar interações: a dependência foi chamada quantas vezes? Em alguns cenários o certo é que nem tenha sido chamada (never).
  • Cenários de exceção: o mock pode devolver null ou lançar erro, para provar que o código trata a falha corretamente.
  • Reiniciar entre testes: cada teste começa com mocks limpos para que nenhum estado vaze de um para o outro.
Estratégia

Pirâmide de testes

Os tipos de teste se organizam em camadas. Quanto mais embaixo, mais rápidos, baratos e numerosos. Quanto mais em cima, mais próximos do uso real, porém mais lentos e frágeis.

TipoFocoDependênciasVelocidade
UnitárioA menor unidade do código, isoladaDublês e mocksMuito rápido
IntegraçãoO código conversando com dependências externasFakes, como banco em memóriaRápido a moderado
Sistema (E2E)A aplicação inteira em execuçãoReais, ou simuladas por ferramentas de API fakeMais lento

No Maven, dá para separar essas execuções com profiles: um perfil roda só os unitários no dia a dia, outro roda os mais pesados na integração contínua, e assim o ciclo de feedback local continua rápido.

Testes de integração em APIs REST

A camada do controlador recebe requisições HTTP e conversa com a camada de serviço. Ela pode ser testada de duas formas complementares:

  • Isolando o controlador: com mocks no lugar dos serviços, para validar apenas o comportamento dele.
  • Fazendo requisições de verdade: com uma ferramenta como o REST-assured (Java), validando status, cabeçalhos e corpo da resposta, sem precisar de uma ferramenta visual.

Esse estilo de escrita segue o padrão given / when / then: given define o que enviar (cabeçalhos, corpo, parâmetros), when é a ação (método e caminho) e then valida a resposta. Abaixo, dois testes contra uma API pública de exemplo, um GET e um POST:

func TestDeveBuscarPostExistente(t *testing.T) {

		t.Fatal(err)

	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		t.Fatalf("esperava 200, recebi %d", resp.StatusCode)

		ID int `json:"id"`
	}

	}
}

#include <assert.h>
#include <curl/curl.h>

#define BASE "https://jsonplaceholder.typicode.com"

static size_t descartar(char *dados, size_t tamanho, size_t n, void *contexto) {
    (void)dados; (void)contexto;
    return tamanho * n;                       /* ignora o corpo da resposta */
}

/* Faz a requisição (POST se houver json) e devolve o status HTTP */
static long requisitar(const char *url, const char *json) {
    CURL *curl = curl_easy_init();
    struct curl_slist *cabecalhos = NULL;
    long status = 0;

    curl_easy_setopt(curl, CURLOPT_URL, url);
    curl_easy_setopt(curl, CURLOPT_WRITEFUNCTION, descartar);
    if (json != NULL) {
        cabecalhos = curl_slist_append(cabecalhos, "Content-Type: application/json");
        curl_easy_setopt(curl, CURLOPT_HTTPHEADER, cabecalhos);
        curl_easy_setopt(curl, CURLOPT_POSTFIELDS, json);
    }
    if (curl_easy_perform(curl) == CURLE_OK) {
        curl_easy_getinfo(curl, CURLINFO_RESPONSE_CODE, &status);
    }
    curl_slist_free_all(cabecalhos);
    curl_easy_cleanup(curl);
    return status;
}

int main(void) {
    /* deve buscar post existente */
    assert(requisitar(BASE "/posts/1", NULL) == 200);

    /* deve criar post */
    assert(requisitar(BASE "/posts",
                      "{\"title\": \"foo\", \"body\": \"bar\", \"userId\": 1}") == 201);
    return 0;
}

Pontos que aprendi

  • Log só na falha: durante o desenvolvimento é útil ver requisição e resposta completas, mas na integração contínua o ideal é mostrar o log apenas quando uma validação falha, para manter a saída limpa.
  • Validar por schema: em vez de conferir campo por campo, é possível validar o corpo da resposta contra um esquema, o que reduz o esforço e garante a estrutura do documento.
  • Explorar antes de automatizar: ferramentas visuais como o Postman (ou Insomnia, ou o Thunder Client no VS Code) ajudam a entender uma API. Com ambientes e variáveis como baseUrl, a mesma coleção roda contra servidores diferentes.
  • Segurança: a lista OWASP das falhas mais comuns em APIs é um ótimo roteiro para pensar em cenários de teste negativos.

BDD, Cucumber e testes de ponta a ponta

O BDD (Behavior-Driven Development) descreve testes na linguagem do negócio, para que analistas, pessoas desenvolvedoras, liderança e gestão falem do mesmo comportamento. A linguagem usada é o Gherkin, e a ferramenta mais conhecida que a executa é o Cucumber.

# language: pt
Funcionalidade: Login
  Como usuário do sistema
  Quero acessar a aplicação
  Para ter acesso às funcionalidades restritas a usuários logados

  Cenário: Login válido
    Dado que o usuário tenha uma conta válida
    Quando efetuar acesso ao sistema
    Então será possível ter acesso às funcionalidades com login

  Cenário: Login inválido
    Dado que o usuário não tenha uma conta existente
    Quando efetuar acesso ao sistema
    Então uma mensagem de aviso sobre o acesso inválido deve ser apresentada

Cada linha do arquivo .feature é ligada a um código de apoio (os steps), que executa a ação por baixo, por exemplo chamando a API com REST-assured. Um executor (runner) integra o Cucumber ao JUnit.

Testes E2E e relatórios

No topo da pirâmide, os testes de sistema validam a aplicação inteira em execução, com dependências reais ou simuladas por APIs falsas. O BDD é uma ótima forma de escrevê-los, porque os cenários se parecem com o que o cliente espera ao usar o produto. Para dar visibilidade aos resultados, o Allure Report gera relatórios navegáveis da execução, e os profiles do Maven permitem rodar só esse conjunto quando necessário.

O que levo daqui

  • TDD é uma forma de pensar: o teste é a especificação, e escrevê-lo primeiro obriga a decidir o comportamento antes da implementação.
  • Um bom teste unitário é rápido, isolado e tem nome que descreve o comportamento esperado.
  • Lint, estilo e cobertura encontram problemas antes mesmo de o teste rodar, e o quality gate impede que eles entrem na branch principal.
  • Dublês só funcionam bem quando as dependências são injetadas por interfaces, o que conecta qualidade diretamente com a arquitetura.
  • A pirâmide guia o investimento: muitos testes unitários, alguns de integração e poucos E2E nos fluxos críticos.
  • BDD aproxima negócio e tecnologia ao descrever o comportamento na linguagem do domínio.
