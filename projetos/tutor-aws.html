O projeto

O Tutor AWS é um tutor em formato de chat para quem estuda para a certificação AWS Certified Cloud Practitioner (CLF-C02). O aluno conversa com um agente de IA que aplica questões, corrige, explica os erros, agenda revisões espaçadas (método Leitner) e monta simulados no formato da prova real: 65 questões, 90 minutos e nota estimada de 100 a 1000.

A regra de ouro

O LLM nunca inventa perguntas, respostas nem correções. As questões vêm de um banco curado, e a correção, a seleção e a nota são feitas por código determinístico. O modelo de linguagem conversa e explica, mas não decide o que está certo. Essa regra orientou quase todas as decisões de arquitetura.

A arquitetura

São quatro serviços, um por contexto do domínio (DDD):

ServiçoContextoResponsabilidade
study-apiEstudoAs regras, o banco de questões e a correção
agent-apiConversaO agente LangGraph e as memórias
mcp-serverIntegraçãoAs tools MCP entre o agente e a API
frontendApresentaçãoO chat e o painel

Stack prevista: Python, FastAPI, LangGraph, MCP, PostgreSQL com pgvector, Redis, Mem0, Langfuse, Next.js, Docker Compose e Terraform. O LLM roda local com Ollama, e o Bedrock é opcional.

Como estou trabalhando

Comecei pela documentação, antes do código. A Fase 0.5 existe para que as decisões difíceis sejam tomadas no papel, onde mudar é barato.

O fluxo com agentes de IA

Eu conduzo o desenvolvimento: defino o produto, dito as diretrizes de arquitetura e organizo o fluxo de trabalho. A execução é feita com o Claude Code e agentes especializados, cada um com um papel:

PapelO que faz
docs-architectEscreve os documentos de arquitetura e domínio
tech-leadRevisa cada PR, verifica executando scripts e pede ajustes até não sobrar nenhum
tech-writerAplica os ajustes e mantém o README, o ROADMAP e as issues em dia
EuDesenvolvo o produto: defino a visão, o escopo e as regras de negócio. Dito as diretrizes de arquitetura que os agentes seguem. Organizo o fluxo de desenvolvimento, com as fases, os papéis dos agentes e as regras de revisão. Respondo as dúvidas de produto, aprovo ou reprovo cada decisão e faço todo merge

As regras do fluxo

  • Toda dúvida vira um item rastreável (D-NN), com as opções, a recomendação de um agente e quem decide.
  • Nenhuma decisão de produto é tomada pelos agentes sem a minha aprovação explícita.
  • O merge é sempre meu.

Verificação

Todo PR de documentação passa por checagens automáticas:

  • links e âncoras;
  • tabelas com o número certo de colunas;
  • diagramas Mermaid validados com o parser fixado na versão 10.9.1;
  • IDs citados que existem de fato;
  • sequências de IDs sem lacunas.

Decisões que valem destacar

O LLM como componente não confiável

O agente pode errar ou sofrer prompt injection. Por isso, as ações que gravam dados passam por guardas em código:

A1

Tools por estado

Só expõe as tools permitidas para o estado da conversa.

A2

Conferência da resposta

Confere a resposta do aluno antes de registrar.

A3

Só questão servida

A API só aceita resposta para uma questão que foi servida.

O envio do simulado é montado pelo código, e não pelo LLM (ADR-0013).

As outras decisões

DecisãoO que significa
O gabarito nunca vazaOs campos de gabarito e explicação não saem da API antes da resposta do aluno. Há testes de "varredura" planejados para garantir isso
Fidelidade à prova realO simulado completo tem 65 questões, 90 minutos de limite duro, envio automático no fim do prazo, nota estimada de 100 a 1000 e aprovação a partir de 700. Tudo conferido no guia oficial da AWS
Banco de questões finito, mas honestoQuando o aluno revê questões que já conhece, o resultado avisa que a nota é menos confiável. O banco cresce com rascunhos gerados por LLM, sempre com revisão humana
Custo sob controleO LLM roda local (Ollama) por padrão. A infraestrutura na AWS está descrita em Terraform, mas só é aplicada de forma pontual, com alerta de orçamento

Lições aprendidas

  1. Decidir no papel é barato. Várias contradições foram encontradas e resolvidas antes de existir código. Um exemplo é a regra das questões não pontuadas, que aparecia de formas diferentes em dois lugares.
  2. A revisão automatizada pega o que o olho não pega. Scripts conferiram links, IDs e contagens, e acharam erros em quase toda rodada.
  3. Delegar não é abdicar. Deleguei decisões técnicas ao tech-lead, mas cada uma voltou para mim num relatório, para aprovar ou reprovar.
  4. Tokens custam. Rodadas longas de revisão gastam muito. Passei a juntar entregas pequenas no mesmo PR e a pedir só correções de conteúdo, sem ajustes cosméticos.
  5. Uma pergunta de produto pode mudar a arquitetura. "O que acontece quando o aluno já viu todas as questões?" virou um ADR novo (rascunhos por LLM com revisão humana), cinco requisitos e três issues de implementação.
