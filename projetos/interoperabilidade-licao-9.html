O contexto

A federação permite que o Unity Catalog atue como uma camada de leitura sobre um metastore existente: os usuários consultam o catálogo legado pelo Unity Catalog, enquanto as tabelas são migradas em etapas.

  • Estabelecer um caminho de migração dos catálogos legados para o Unity Catalog.
  • Manter a continuidade operacional.
  • Usar a federação como uma tecnologia-ponte, para a migração em fases.
  • Consolidar a governança gradualmente, minimizando as interrupções.

Configurando foreign catalogs

Os foreign catalogs são configurados encadeando IAM roles, credenciais de storage, um objeto de connection e o próprio foreign catalog. Os quatro passos para o AWS Glue:

  1. Criar a(s) IAM Role(s) na AWS, com acesso ao Glue e ao storage S3 subjacente.
  2. Criar as credenciais de storage e de serviço na Databricks, usando a(s) role(s).
  3. Criar um objeto Connection na Databricks.
  4. Criar o Foreign Catalog, espelhando o banco do Glue.

A abordagem varia por provedor, e o mesmo padrão vale para o Hive Metastore, o Snowflake e outras fontes federadas. Os passos são os da Demo 5, com o detalhe das duas roles, dos external IDs e da external location.

A migração para tabelas gerenciadas

A federação é um estado temporário. O objetivo de longo prazo é converter as tabelas foreign em tabelas gerenciadas pelo Unity Catalog, para liberar o conjunto completo de recursos.

BenefícioDetalhe
Conjunto completo de recursosOs recursos de otimização, o monitoramento de qualidade e os ganhos de desempenho
Leitura e escritaConverte tabelas foreign, somente leitura, em tabelas gerenciadas de leitura e escrita
Governança aprimoradaGestão centralizada de metadados, com políticas unificadas

Ganhos de desempenhoMelhorias significativas em relação às foreign tables

Os comandos de migração

Dois ALTER TABLE movem a tabela de foreign para external e depois para managed. Na página, o nome da tabela aparece em branco, como um placeholder:

-- Converter tabela foreign em external
ALTER TABLE <tabela> SET EXTERNAL;

-- Converter tabela external em managed
ALTER TABLE <tabela> SET MANAGED;

A migração in-place é a abordagem preferida, porque mantém os identificadores, as ACLs e as consultas downstream inalterados: preserva o namespace (os mesmos identificadores nas consultas), a continuidade de permissões (as ACLs intactas), exige mudanças mínimas de código, reduz o risco (com a possibilidade de rollback) e tem zero downtime (as cargas de produção continuam durante a migração).

Testes e validação

Antes de confirmar a migração, dry runs e verificações permitem confirmar a compatibilidade sem alterar o estado das tabelas.

O dry run

ALTER TABLE {foreign_table} SET {EXTERNAL|MANAGED} DRY RUN

Valida a migração sem executá-la. As verificações da fase de dry run são:

  • a compatibilidade do formato da tabela (Delta, Iceberg e outros);
  • as permissões do local de storage;
  • a compatibilidade de schema;
  • os benchmarks de desempenho.

O rollback

Reverte tanto o estado da tabela quanto o dos dados. O comando UNSET MANAGED está disponível para as tabelas gerenciadas, e o RESTORE volta a versões anteriores.

As considerações comuns

  • As tabelas gerenciadas exigem um storage location do Unity Catalog.
  • A cópia inicial dos dados pode causar uma latência temporária.
  • As tabelas apoiadas em DBFS exigem um tratamento especial.
  • Use utilitários Python para a conversão em lote de várias tabelas.

Key Takeaways

  • A federação é uma ponte zero-downtime para migrar ao Unity Catalog.
  • A migração in-place preserva os namespaces, as permissões e a compatibilidade das consultas.
  • O suporte a dry run permite validar com segurança antes de confirmar a migração.
  • As tabelas gerenciadas liberam o conjunto completo de recursos do Unity Catalog, incluindo o Predictive Optimization.

O que guardar: a federação de um metastore legado é temporária. O caminho é registrar o legado como foreign catalog (IAM roles, credenciais, connection e foreign catalog), consultar pelo Unity Catalog e migrar tabela a tabela, no local: SET EXTERNAL e depois SET MANAGED. Antes, faz-se o DRY RUN, e há rollback pelo UNSET MANAGED e pelo RESTORE. O ganho é o conjunto completo de recursos, com a escrita e o Predictive Optimization.
