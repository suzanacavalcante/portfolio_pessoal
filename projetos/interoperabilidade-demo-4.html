Federation to SQL Server and Snowflake

Data Interoperability with Unity Catalog · Demo 4

Em desenvolvimento

Esta demo, de cerca de 8 minutos e meio, mostra o Lakehouse Federation, o "outro lado" da interoperabilidade. Nas demos anteriores, o Unity Catalog servia tabelas a motores externos pelo Iceberg REST. Agora o Unity Catalog alcança sistemas externos e os consulta no lugar, sem mover dados: primeiro o SQL Server, depois o Snowflake.

Estas anotações partem de um resumo da demo, não da transcrição. Segundo o resumo, a única legenda do vídeo está em chinês simplificado, e o resumo foi feito a partir dela. O resumo não traz o texto dos comandos, e por isso não escrevi código aqui.

Pré-requisitos

  • No Databricks: metastore admin (ou, no mínimo, o privilégio CREATE CONNECTION).
  • No SQL Server: um login sysadmin, para provisionar o login de federação.
  • No Snowflake: account admin.
  • Conectividade de rede do workspace para as duas fontes.

O padrão: connection e foreign catalog

  • A connection é um objeto do Unity Catalog que guarda o host, a porta e as credenciais da fonte. É criada uma vez e pode ser reutilizada em vários foreign catalogs. As opções dependem do sistema de origem.
  • O foreign catalog referencia um banco da fonte e o expõe como um catálogo do Unity Catalog.

SQL Server

A fonte é uma instância SQL Server com o banco de exemplo AdventureWorksDW (mostrado no SSMS).

Login e connection

  1. No SQL Server, provisiona-se um login SQL dedicado, com menor privilégio: cria-se o login, cria-se o usuário do banco e adiciona-se a uma role com acesso aos dados, com uma instrução para validar as credenciais.
  2. No Unity Catalog, cria-se a connection. Aqui se usa usuário e senha, só para a clareza da demo.
  3. Valida-se com o DESCRIBE CONNECTION EXTENDED.

Em produção: não use a senha escrita direto na connection. Use um secret scope.

Foreign catalog

Com a connection, cria-se um foreign catalog que referencia o banco AdventureWorksDW. O DESCRIBE mostra o tipo foreign. Na exploração:

  • o SHOW SCHEMAS devolve a mesma lista que o SQL Server direto;
  • o SHOW TABLES no schema dbo lista as tabelas fato e dimensão;
  • o DESCRIBE da dimensão account mostra as colunas, retornadas do SQL Server;
  • uma consulta sobre fato e dimensão do foreign catalog retorna dados.

Snowflake

O padrão é semelhante, mas como o Snowflake depreciou a autenticação só por senha, usa-se um par de chaves RSA.

No Snowflake

  1. Cria-se uma role de federação.
  2. Cria-se um service user, que usa essa role, e concede-se a role ao usuário.
  3. Concedem-se à role os privilégios nos objetos permitidos.
  4. Atribui-se a chave pública ao usuário.
  5. Valida-se com o DESCRIBE USER e o SHOW GRANTS.

No Unity Catalog

A connection do Snowflake tem propriedades diferentes das do SQL Server: o warehouse virtual, a role criada e a pem_private_key, que vem de um secret scope (Snowflake Migration). O DESCRIBE CONNECTION EXTENDED mostra as opções.

Depois, cria-se um foreign catalog para o banco de dados de amostra do Snowflake. O SHOW SCHEMAS mostra os schemas TPC-DS e TPC-H, lista-se as tabelas do tpch_sf_1 e faz-se o DESCRIBE da tabela nation.

O ponto alto: uma única SQL faz um join entre a nation do Snowflake e a samples.tpch.nation do Databricks, atravessando dois sistemas sem mover dados.

Pushdown e conclusões

As duas connections suportam o predicate pushdown, em que os filtros são enviados à fonte. Dá para ver pelo EXPLAIN. Há diferenças sutis entre os conectores (Snowflake e SQL Server) a considerar.

PontoO que lembrar
O padrãoConnection + foreign catalog é o padrão geral de federação, igual para o SQL Server, o Snowflake e qualquer outra fonte suportada
A configuraçãoO provisionamento na fonte é desacoplado da configuração no Databricks, então há configuração nas duas pontas
A governançaO Unity Catalog governa a federação, mas, diferente das demos de Iceberg e UniForm, os dados são governados pela plataforma de origem
Joins entre plataformasSão possíveis em uma única SQL, e o planejador empurra os filtros e as agregações quando possível (confirma-se com o EXPLAIN FORMATTED)

Ligação com as outras páginas: a connection e o foreign catalog são os conceitos que a lição Centralized Governance and Visibility apresentou como a base da federação lakehouse. E o CREATE CONNECTION é um dos privilégios do metastore na lição Privileges in Unity Catalog. As ligações são minhas.

O que guardar: a federação é o caminho contrário do Iceberg REST: em vez de servir os dados a um engine externo, o Unity Catalog consulta a fonte no lugar. O padrão é criar uma connection (com as credenciais, de preferência em um secret scope) e um foreign catalog por banco. A fonte é configurada com o menor privilégio (no Snowflake, com um par de chaves RSA). Os filtros são empurrados à fonte, e dá para fazer joins entre plataformas, mas a governança dos dados continua na plataforma de origem.
